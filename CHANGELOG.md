## [Unreleased]

### Added
- ci: a workflow of its own builds the Docker image and runs it: `.github/workflows/image.yml`, with `scripts/image-check.mjs`. Until now no job built the image by itself (`docker.yml` publishes it by hand). Neither the image nor production changes.
  - **What the job checks.** `docker build` of the repository. A container started as the image starts (its own entry point and command, a named volume at `/app/world`, made-up settings, no port published) becomes `healthy`, runs a `node build/index.js` process and answers `GET /status` with the build's `COMMIT_HASH`. `docker stop -t 10` (SIGTERM) and, on a second container, `docker stop --signal SIGINT -t 5` (Fly's documented default signal and timeout) each end with exit code 0, within 8 s and 4 s, with the server's `saving the world before exit` and `[network] final save complete` lines in the log and none of the lines that say that something was not stopped or not saved (`[network] not persisted`, `[server] stopping the world failed`, `… was not loaded; changes will not be saved` among them: `NOT_STOPPED_OR_SAVED`, each quoted from its source), whatever the exit code. A third container on the same volume becomes healthy.
  - **What it records.** Who PID 1 is and which of the two signals it handles, whether a shell sits between it and the server, the uids and the image's configuration: in the job's output and in the `image-check` artifact, with each container's log.
  - **When it runs.** For a pull request or a push to `main` that changes the Dockerfile, `.dockerignore`, `package.json`, the lock file, `.nvmrc`, `scripts/build*.mjs`, `scripts/lib/`, `src/server/`, `src/core/` (bundled into the server, the final save among it), the script or the workflow; weekly; by hand. It is not a required check (a path-filtered one stays pending on every other pull request). It has `contents: read`, uses no Docker action, runs no `npm ci` and pushes nothing. The step runs the script with `exec`, so that a cancelled run's SIGINT reaches Node rather than Bash.
  - **Not covered.** What Fly does differently from `docker run` (its own init, its signal and timeout, who owns a volume, its health checks), other architectures, a world with content: DOCKER.md, "Checked in CI". Nothing is changed in the world before the stops.
  - **The script.** `--model=current` is the image as it is today and the only model; an unknown one is an error. `--dry-run` prints the docker commands of a run without running any. What it creates carries a random id of the run and is removed at the end, also after a failure or a signal.
  - **A cancelled run.** GitHub sends the step SIGINT, SIGTERM 7.5 s later, and kills it 2.5 s after that. On the first signal the docker command in flight is ended unless it creates or removes something (a `docker stop` of a container that does not stop, a `logs`, an `exec`, the build, the wait between health polls), and the cleanup starts at once: a `docker run` or `volume create` in flight gets 1.5 s, each of the three removals 2 s, 7.5 s in all. A second signal does not stop the cleanup. The exit code is 130 or 143, after the first signal.
  - **Tests.** `test/imageCheck.test.js`: the BusyBox `ps` tree, `/proc/1/status`, the verdict on a stop and the order of the docker commands, on canned output and against a stand-in for the docker CLI, and a SIGINT while that stand-in's `docker stop` never returns (the stop is killed, the three removals run in order) and a second signal during the cleanup. Each line that fails a stop is produced by the real signal handler (`src/server/shutdown.js`) where it can be, else written as the source prints it; a source-text tripwire fails on a log call in `installShutdown` or on the final save's path in `ServerNetwork.js` that the list neither forbids nor allows with a reason. No test runs Docker.
  - `scripts/prod-smoke.mjs` takes the server's settings from the module the image check uses (`scripts/lib/startEnv.mjs`); the settings are the same as before.

- client, tips: the tip form tells the payer more about who is paid and what is known (`src/core/extras/tipOutcome.js`). All of it is information for the payer, not a control: anything running in the page can change both the form and the request the wallet gets. The form limits no amount either: the built-in tokens have a maximum per tip (1,000 JPYC, 10 USDC), a custom token has one only if its spec gives it (`:max`), and none of this limits what code running in the page asks a wallet for.
  - **The recipient's short address.** The sending step shows the recipient's name and short address (`0x1563…5508`) once the server's tip intent has arrived, and the "Sent" and "may have been sent" texts carry it. For an ERC-20 transfer a wallet shows the token contract as "to", and some mobile wallets do not decode the recipient at all: the form says that the wallet may show the token contract and may not show this address. The address is disclosed to the sender at the same moment as before (the intent). In these texts the name is shown without the bidirectional control characters U+202A–U+202E, U+2066–U+2069, U+200E, U+200F and U+061C, and the form renders it in a `<bdi>` of its own and the address in an element of its own with `dir="ltr"` (a name with U+202E in it reordered the address and the sentence after it). The name elsewhere in the interface (the form's title and confirmation sentence, the Players list, nametags, chat) is shown as before.
  - **Same name.** When another connected player has the recipient's name, the form says so. Two names are the same after Unicode NFKC (full-width `Ｂｏｂ` folds to `Bob`), collapsing every run of white space to one space (tabs, line breaks and the Unicode spaces included, so `Bob<tab>Smith` is `Bob Smith`: this comes first, as a tab is a control character too), removing characters that are not drawn (zero-width and other default-ignorable, control and format characters), lower-casing, and trimming. **Not caught:** look-alike letters of another script (a Cyrillic `В` and `о` in "Bob"), and any name that only resembles another. The payer's own name does not count.
  - **A note of the request.** Just before the wallet is asked to send, the browser writes a note to `localStorage` under a key of its own, `evmTipRequest:` and an id made for the note. A note holds the recipient's display name, the short address, the amount, the token symbol, the time of that moment and that random id: not the full address, not the payer's address, not a transaction hash. That key is removed when the transaction hash has been handed to the server or the wallet explicitly rejected, and no other: nothing is read to decide what to remove, so a note another tab writes meanwhile stays; a request that never reached the wallet writes none. The ten minutes count from the request to the wallet, not from the intent (the account and network prompts before it can take minutes). A note that is left (a page reloaded on the way back from a wallet app, which iOS often does; a deploy or a lost connection seconds after a send; an answer that was not clear) is shown under the wallet button, whether the panel is open or folded and before any sign-in: "A tip may have been sent: 100 JPYC to Bob (0x1563…5508). … Check your wallet's activity before sending it again.", each until its own Dismiss (which removes that note's key, by the id shown) or until it is ten minutes old. The first four notes are shown, newest first, and a line says how many more there are ("2 more notes like these are kept in this browser. They are shown here as these are dismissed."); dismissing one brings the next into view. A note older than ten minutes is removed when a page of this site next reads the notes: nothing removes it while no such page is open, so it can stay in the browser's storage until then, or until the browser clears the site's data. A read never removes a well-formed note younger than ten minutes; under the prefix it removes the expired ones and what is not a note: malformed, longer than 2,048 characters, kept under a key that is not its own, or timed more than ten minutes ahead of the reader's clock (one up to ten minutes ahead is kept and expires ten minutes after its own time). A read finds every note that the storage lets it read, whatever else is under the prefix, and the page reads again a moment after another tab changes this site's storage (a retry, which can be cut short like the first read); the count the notice gives is of the notes that were read, and it says "at least" when a value could not be. A page learns of another tab's note when it next reads the storage (its load, the end of a send of its own, a Dismiss, a note's ten minutes). Anything running on this origin in this browser profile can read the notes, including other pages and worlds served from the same origin; other sites cannot. It is this browser's memory of a request, not a record of a payment: it says nothing about what the wallet did, another browser never sees it, and storage that is blocked or cleared means no note, as a full one can for a new note (the form and the send do not depend on it).
  - **A world that does not confirm.** The world tells its clients whether it confirms tips: `confirmsTips` in the `evmWalletStatus` of a successful sign-in (only where tips are on) and `confirms` in each accepted `evmTipIntent`. It is `false` when the server has no `EVM_RPC_URL_<chainId>` for the sign-in chain, and from the moment its RPC left the `finalized` tag unanswered (tips end `no_finality`) until a later read of the tag works. The form then says, on the confirmation step and again on the sending step, before the wallet is asked: "This world is not confirming tips right now. The transfer still goes through your wallet and may not be confirmed or announced here." ("May not": after a `no_finality` a later read of the tag can work, and a tip sent meanwhile can still be confirmed and announced.) When the intent is the first to say so (the world had said yes at sign-in, or nothing), the send stops on a step that says it, before the wallet is asked anything (no account, network or transfer request), and goes on only when the payer presses **Send anyway**; Cancel goes back to the amount. Send anyway acts on that intent for 5 minutes of time elapsed in the page since the intent arrived (`performance.now()`, which a change of the wall clock does not move; the server keeps the tip request for 10 minutes from issuing it, and the intent carries neither time): later, the wallet is asked nothing and the form says "This request expired before you answered. Nothing was sent. Start again.", back at the amount, where Next opens the confirmation and Send tip asks for a new intent. A send without that step goes on at once and is not timed. A sender used to learn this only after paying. A tip of the player's own that comes back `no_rpc` or `no_finality` counts as the world's word too, until the next sign-in or intent says otherwise. A world that has not said (an older server) shows nothing.

- server: the world page is now tried against a full Content-Security-Policy, as `Content-Security-Policy-Report-Only`. **This protects nothing**: a browser loads and runs everything exactly as before, and posts what the policy would have refused. It is here to learn what enforcing the policy would break for real visitors (a wallet extension that puts a script into the page, a wallet's in-app browser, a frame a wallet library opens) before anything is enforced; the four directives that were already enforced are unchanged.
  - **The policy.** `default-src 'self'`; scripts from the page's own origin, with the response's nonce (the page's two inline scripts carry it; a new one each response, and the page now says `Cache-Control: no-cache`), or from the script editor's folder on cdnjs, with `'unsafe-eval'` (app scripts are evaluated); styles from the page's origin, inline, or that folder; images, media and connections from anywhere; workers from the page's origin and `blob:`; frames from WalletConnect's two Verify hosts only. Enforced, it would stop an inline script or handler that got into the page and scripts of other hosts. It would not stop text that reaches an `eval` of the page's own code, injected CSS, data leaving through an image or a request, or whoever controls that cdnjs folder; and app scripts are not limited by it at all.
  - **The reports.** `POST /csp-report`: 20 posts a minute from one address (an IPv6 address counting with its /64) and 600 a minute in all, counted when the request reaches the route and whatever the post turns out to be, the rest answered 429; the route keeps and parses a body of 8 KiB at most as sent, and a compressed one is refused (415), never decompressed. A post refused for the rate, its encoding, its type or its length is answered with `Connection: close`. These bound what the route does with a post, not what the HTTP layer reads from a connection: bytes that are sent are read and thrown away in cases no route decides, here as on every path of the server. The server writes a line the first time an hour sees a kind of report, again at 10, 100, 1000 of it, and one line of totals for an hour that had a report or a post over the rate: `[csp] report-only: <directive> would refuse <origin, scheme or the browser's word>, asked by <path of a file of the page, or an origin or scheme>`. An hour holds 100 kinds; more are only counted. No query string, page address, referrer, script sample or extension id is kept. Anyone can post to this route: a line is what was posted, not proof of what a browser did, and someone can fill an hour's table with made-up kinds.
  - **Not covered.** The other static pages (`terms.html`) are not tried against this policy. Only the old `report-uri` form is sent (every engine posts it; the newer Reporting API is not used). The end-to-end runs (the world, uploads, the script editor with its workers, an injected wallet, the WalletConnect sheet, tips) report nothing in Chromium and WebKit; real wallet extensions, wallet in-app browsers, WalletConnect's relay and Verify frame against the real service, and voice were not tried and are what the reports are for.

  - **What they say.** The world is non-custodial and takes no part in transfers between players. Minors need a guardian's consent.
  - **Tips.**
    - **The address.** The opt-in is visible to the players in the world. The recipient's address goes to a sender when they start a tip, even one they never send, and it cannot be taken back.
    - **Sending.** Transfers go wallet to wallet on Polygon with no fee; the sender pays gas. There are per-token minimums and rate limits, and transfers cannot be undone.
    - **Confirmation.** "Could not confirm" does not mean the tip was not sent.
    - **Announcements.** Confirmed tips are announced in chat with display names, amount and token, sometimes to the recipient only. World apps are told the same with player ids. Neither gets addresses or hashes.
    - **No goods.** Tips buy nothing; an app's own perks are its author's responsibility. Recipients handle their own taxes.
  - **Data.** Wallet address, verified state and the tips setting are kept only in server memory, for the checks (sign-in, tip confirmation, token and NFT holdings). They are never stored in the database and are gone when the server restarts. RPC and WalletConnect get what they need to check.

  - **Links.** The Receive tips switch and the tip confirmation link the terms. Both now say the world takes no fee, and the confirmation also says it is not a party to the transfer. Keys in the tips block stay out of the world's controls, so Tab reaches the link and Enter opens it without the chat; Escape still folds the panel.
- wallet: smart-contract wallets (EIP-1271, and EIP-6492 for accounts not deployed yet, such as Myna Wallet) can sign in with EVM when the server has `EVM_RPC_URL_<chainId>` for the sign-in chain.
  - **Check.** EOA signatures are still checked locally. Any other signature gets one deployless `eth_call` of the ERC-6492 universal validator at `latest`. The bytecode is copied from viem 2.57.8 and pinned in tests. The call is limited to 10M gas and 8 s, at most 4 at once and about 30 a minute per server.
  - **Results.** A revert means a wrong signature. A rate limit, timeout or unexpected answer means the check is unavailable, logged once per kind.
  - **Reasons.** `evmWalletStatus.reason` can now also be `contract_unsupported` (no RPC for the chain) or `unavailable`, each with its own message. The packet table and `PROTOCOL_VERSION` are unchanged.

  - **Behaviour.** An adapter on SignClient makes the session look like an injected wallet to the existing SIWE and tip code: accounts on the sign-in chain only (following the wallet's account switches), the network switch answered locally, rejections as 4001, and a session ended in the wallet seen as a disconnect. Each pairing has its own link; the relay gets 20 s to answer; Cancel (also while the sign-in waits in the wallet) ends the pending pairing and closes a session that arrives late. Sessions are ended by topic, waiting at most 10 s for the relay before they are dropped locally. A wallet's link back is used only when it is an https link or an app scheme.

- wallet: tips are confirmed on chain and announced (P2b) when the server has `EVM_RPC_URL_<chainId>` for the sign-in chain.
  - **Reporting.** Each tip intent now carries a server ticket. After the wallet returns the transaction hash, the client reports `{ ticket, txHash }` (new packets `evmTip` / `evmTipStatus`, appended; protocol version unchanged).
  - **Checking.** The server polls a shared, budgeted watcher. It matches only the token's `Transfer` log (sender, recipient, exact amount), not `receipt.from` or `receipt.to`, so EIP-7702 and sponsored transactions work. It waits for the `finalized` block, checks the block hash, and refuses transactions from a block more than about 30 s older than the ticket.
  - **Results.** Only the sender gets `watching`, then `confirmed`, `failed` or `unverified`. An unconfirmed tip can be reported again once.
  - **Duplicates.** A sender's transfer in a transaction is counted once while the server process remembers it (see Fixed), and is only marked seen when confirmed, so another player's report of the same hash cannot block it.
  - **Announcement.** A confirmed tip is announced as a system chat message, paced to 3 at once then one per 3 s, and one per sender per 30 s; otherwise only the recipient is told.
  - **Script event.** Server scripts get the protected `tip` event, with no addresses or transaction hash.
  - **RPC errors.** `RpcError` now separates JSON-RPC error answers from transport failures.
- wallet: tips between players (JPYC / USDC on Polygon) behind `PUBLIC_EVM_TIP_TOKENS`. A verified player opts in with **Receive tips**; other players see only an `evmTips` flag and a tip button in the Players list. Sending asks the server for a tip intent (verified senders only, 3 per socket then 1 per 10 s, never to the same wallet, per-token minimum) that returns the recipient's verified address and the exact amount; the sender's wallet then sends one ERC-20 `transfer` straight to that address after checking its account and chain (switching to, or adding, Polygon). The server never holds funds or builds transactions, and tips are not yet verified on-chain or announced.
- apps: `player.getEvmHolding(spec)` for server scripts checks whether a player's verified EVM wallet holds an ERC-721 / ERC-1155 token through a server-only `EVM_RPC_URL_<chainId>` (cached 30 s, shared budget, fail-closed `known: false`), and the protected server event `evmWallet` reports verification changes. Example app: `docs/scripting/examples/nft-gate.js` (works with OpenPay license NFT ids).
- wallet: EVM wallets (MetaMask, Rabby, any EIP-6963 or injected `window.ethereum` wallet) can prove address ownership next to Solana, behind `PUBLIC_EVM_CHAIN_IDS` (for example `137`; empty keeps EVM off and the world behaves as before). The server builds a Sign-In with Ethereum (EIP-4361) message bound to the page host, URI, the first configured chain, a 64-character hex nonce and a 60-second expiry, and verifies the signature against the message it stored (EOA only; smart-account EIP-1271/6492 signatures are refused for now). Verification is per connection, is not stored, is not sent to other players and does not change rank: builder access is still granted by the Solana token only. Solana and EVM keep separate sessions, cooldowns and attempt counters, so neither cancels the other. The wallet panel gets Solana / EVM tabs when both are enabled (the choice is remembered with the open/closed state); the EVM tab lists the announced wallets and shows the verified address. `viem` 2.57.8 is a server-only dependency (the browser bundle does not include it).

A remote player's voice loudness opens their avatar's mouth (the first VRM mouth preset among aa/oh/ou/ih/ee), measured on a listen-only WebAudio branch beside playback and smoothed (60 ms attack, 120 ms release). Mouths close for moderator mute, a disabled voice, a suspended AudioContext or beyond 20 m. Each avatar instance writes its own clone's morphs, so players sharing an avatar never mirror each other. Settings › Audio › Lip Sync, on by default on desktop and off on touch devices. Nothing is sent over the network; protocol and server are unchanged.

- apps: client-local `player.getTokenBalance()` and the protected `wallet` event expose verified COO balances to world scripts; reads are cached and local gates affect only the player’s own screen.
- server: per-socket wallet verification, signature-free builder rechecks, and one shared balance service with fresh-only grants and bounded requests.
- tests: Phase 3b-1 real-PhysX availability regressions and server/browser E2E probes cover contact mutation, deferred removal and repeated static-body calls, with independent falling-body and tick checks.

- core: `MONITOR_TICK=1` logs a per-minute summary of server tick times (mean/median/p90/max). (An earlier wording said the last window was also on `/status`; it never was.)
- ci: an end-to-end Playwright job (`test/e2e/`, Chromium/WebKit/Firefox) runs on pull requests and on demand
- server: upload rate limits and quotas (`UPLOAD_*` envs): per-user and global concurrency, per-minute rates and daily byte quotas per user and per address, a shared daily budget for users without a stored or wallet-verified builder rank (wallet-granted builders are limited per wallet, and a slot of the total is kept for stored-rank users), a transfer deadline per admitted upload, and a free-space floor for local assets. Refused upgrades receive HTTP 503 with `Retry-After: 10` before any database lookup. Raising or disabling `WS_MAX_SOCKETS` raises or removes the default 64 MiB total write-backlog bound.

- server: AI actions have a budget (`src/server/aiBudget.js`; see Security). A builder runs one action (create, edit or fix) at a time and 20 an hour; the world runs 2 at once and 60 an hour (`AI_MAX_PER_USER_PER_HOUR`, `AI_MAX_PER_HOUR`, `AI_MAX_CONCURRENT`). - client: a model, avatar or emote may only use what is inside its file. A `.gltf` or `.glb` that names an external buffer (a `.bin` by URL or relative path) fails its load; one that names an external image loads without that texture. Embedded buffers and images, and `data:` URIs, load as before. Until now a file's absolute dependency URLs (`https://…`) were fetched, for an uploaded `.glb` or `.vrm` as for a remote file, outside the loader's size limits and deadlines; only relative ones never resolved (files are parsed without a base path). A file that relied on absolute URLs now fails (buffers) or loads without those textures (images). The server cannot load external files either.
- client: an image a model, avatar or emote decodes must be a PNG, JPEG or WebP, by its bytes whatever `mimeType` it declares; a file with any other image it decodes (GIF, BMP) fails its load with a reason. An image used only through `KHR_texture_basisu` is never decoded (this client has no KTX2 decoder and uses the fallback image). AVIF textures inside models are not decoded either, in any browser: the parser takes `EXT_texture_avif` as unsupported and uses the fallback image (an AVIF image cannot be sized before its decode; a file that requires the extension fails its load with a reason). Stand-alone AVIF images still go to the browser as before. An image named by URL is not fetched, as before. The bundled models and avatar decode PNG and WebP only. Stand-alone images keep every format the browser decodes.
- client: an asset in the world's own store is loaded and kept once whatever its query or hash: `asset://x.glb?s=2` and `asset://x.glb` are one download and one result, and `loader.get`/`has` answer for either. Playback options in an emote's query (`?s=`, `?l=`, `?g=`) still apply, since the avatar reads them from the URL it was given. A URL from another host keeps its query, which can name a different resource.
- server: remote models, emotes and scripts named by a blueprint are fetched through one outbound request policy (`src/core/extras/outboundFetch.js`). App scripts' `fetch` goes through it too, on the server and the node agent (in a browser it is the browser's fetch, as before): see **Scripts** below. Avatars are stubs on the server and are not fetched.
  - **Where it may connect.** `http` and `https` only, no credentials in the URL, and only public addresses. IPv4: loopback, private, link-local (cloud metadata), carrier-NAT and the other special ranges are refused. IPv6: an address is refused when it is not global unicast (`2000::/3`), so loopback, link-local, unique-local, multicast, NAT64 and the IPv4-compatible and IPv4-translated forms are refused, or when it is in a special-purpose range inside it (the `2001::/23` protocol assignments such as Teredo and ORCHID, documentation, 6to4) or in the returned 6bone space `3ffe::/16`. An IPv4-mapped address follows the IPv4 rules. No allocation table is kept: an unallocated block inside `2000::/3` is admitted (it has no route on the public internet), so new address space works once it is allocated. The host is resolved once through DNS (A and AAAA; the hosts file is not consulted), every address must be public, and the connection is made to a checked address, so a second DNS answer cannot change the destination. The first IPv4 answer is used, or the first IPv6 one; if connecting to it fails (refused or unreachable) or has not connected within a third of the time left, but at least 250 ms, one more checked answer is tried, of the other family when there is one. That attempt is still within the one deadline: a deadline shorter than the first attempt's 250 ms ends the request before it. The connected address is checked again before anything is sent, and TLS is verified for the URL's name. Redirects (at most 3) pass the same checks, and the body of a redirect that is followed is not read.
  - **Limits.** One deadline covers the whole request: resolving, connecting, redirects and the body. A remote load may take 30 s and 32 MiB of decoded body. At most 16 requests run at once and more are refused rather than queued; a request keeps its slot until its DNS queries have ended. The slots cover the exchanges only, not what a caller does with a response afterwards (the loader's parsing has its own bound, below). Responses being received share a 64 MiB budget, which covers a request until its response is handed over (the body is held once, as received); what the caller then reads or keeps is the caller's memory. The handed-over body still follows the caller's `signal`, as fetch's does: an abort before it is read to the end (an empty body included) makes reading it reject with the signal's reason, an `AbortError` for a plain `abort()`. A response without a body (HEAD, 204, 205, 304) has nothing to abort: reading it after an abort gives `''`, as native fetch does on Node 24 (on Node 22 native fetch rejects). Bodies are decoded from gzip and deflate only, and a response without a body (HEAD, 204, 205, 304) is not decoded.
  - **Requests.** The options are fetch's: `method` (GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS), `headers` (repeated names are combined as fetch combines them, Cookie with `; `; every header sent, the ones the policy adds included (Host, Accept-Encoding, `Connection: close`, Content-Length, which is also `0` for a POST, PUT or PATCH without a body, and an inferred Content-Type), is set explicitly, so Node adds none, and is validated and counted before anything is resolved or sent: at most 64 and 16 KiB of names and values in all, so a GET, HEAD, DELETE or OPTIONS without a body leaves 61 to the caller and a POST of a string 59; a Blob's type must be a string), `body` (a string, an ArrayBuffer, a typed array or DataView, or a Blob, at most 1 MiB, with the Content-Type fetch infers), `signal` and `redirect` (`follow`, `manual` returns the redirect, `error` rejects; an empty `Location` is the same URL again). A request that a redirect turns into a GET loses its body and fetch's request-body headers (Content-Encoding, Content-Language, Content-Location, Content-Type). `mode`, `credentials` and `cache` mean nothing on the server and are ignored; any other option, and a GET or HEAD with a body, is refused.
  - **Trusted origins.** The world's own assets URL is exempt from the address check (it is local in development and may be a private object store). `OUTBOUND_TRUSTED_ORIGINS` lists further origins, comma separated. Upgrade note: a world whose blueprints load from a host on a private network must list that origin.
  - **Scripts.** A script's `fetch()` on the server used the global fetch, so a script could request the server's own loopback, its private network and cloud metadata addresses, with responses of any size. It is now made by the same policy (an instance of its own, so scripts' requests and the server's remote loads cannot take each other's slots or memory), with the app as the caller: public addresses only (and the trusted origins), a response of at most 8 MiB of decoded body, a request body of at most 1 MiB, 15 s for the whole request, at most 3 redirects, and at most 4 requests in flight per app (16 for all apps together); a request beyond those is refused, not queued, and its promise rejects with a `TypeError` whose message says why (`outbound request refused: …`, `outbound request failed: …`). The response resolves once its whole body has arrived (it used to resolve at the headers), so an endpoint that keeps its response open fails at the 15 s. The headers the policy sets or drops (Host, Connection, Content-Length, Accept-Encoding, Transfer-Encoding, Proxy-Authorization and the other hop-by-hop ones) are no longer the script's to send, and a decompressed response has no `content-encoding` or `content-length` header. A request body is sized and sent by its own bytes: an `ArrayBuffer` or view is copied by the host without running the constructor it names (`Symbol.species`) or reading `byteLength`, `byteOffset` or `buffer` properties a script put on it (a subclass with an own `byteLength` of 1 used to pass the request-size check with a megabyte of bytes). A `data:` URL and an object URL made for a script are still read locally, by the platform's fetch (no other `blob:` URL of the process is); the limits above are those of `http`/`https` requests and do not apply to these reads, which hand over bytes the script already holds. They are read to the end without the run's abort signal: on Node 24, aborting the signal of such a response while its body was unread (an app removed or rebuilt after `fetch('data:…')`) threw from the platform's abort listener and ended the server process; Node 22, which the Docker image pins, is not affected. Upgrade notes: a server-side script that calls a service on a private address needs that origin in `OUTBOUND_TRUSTED_ORIGINS`; one that starts more than 4 requests at once must wait for some to finish; a response compressed with anything but gzip or deflate is refused (the request asks for those only). See docs/scripting/Utils.md, Fetch.
  - **Models.** On the server a model or emote may only use what is inside its file (`data:` and `blob:` URIs): nothing outside the file is ever requested. An external buffer fails the load; an external image is not fetched, and the model loads without it (the server draws nothing).
  - **Cache.** The server loader keeps at most 512 finished loads of every kind and location (the world's store and remote URLs alike), the least recently used leaving first. A load in progress is never dropped, so while more than 512 are in progress the cache holds them all. What loads in progress hold is bounded per kind: models and emotes, local and remote alike, are read and parsed in 4 turns (a turn covers the read and the parse, and the others wait in order without having read anything). A deadline frees a turn whose read (30 s) or parse (60 s) does not settle: that load fails and the turn goes to the next. A read given up is cancelled (its outbound request is aborted, a local read stops); a parse cannot be, so a parse whose turn expired may still be running, and holding its memory, until it settles, outside the 4 turns. A deadline cannot interrupt a parse that blocks the event loop, and a phase that completes before its timer has run is accepted however long it took, so a large but valid model still loads on a slow host. A destroyed loader fails the loads waiting and those in a turn, and starts nothing for them, a remote script takes one of the 16 outbound slots while it downloads, and a local script read has no bound of its own. A load that finishes after it was replaced or after the loader was destroyed writes nothing. One resource has one entry whatever its spelling (surrounding spaces, a fragment, a default port); an `asset://` name and the assets URL it maps to share one where assets are read over HTTP, while with a local assets directory the file and the URL are separate resources and keep separate entries. A query names another resource. Failed loads are not kept, so a URL that starts working is loaded on the next request. Every avatar shares one entry.

- tooling: `npm run world:backup` archives one consistent state of the SQLite database (P13: SRV-13).

The database now goes in as a copy made by SQLite's own backup; the live file, its log and its lock file are left out. A database that stays locked for the whole wait fails the backup (the library reports that case as a backup of nothing, which would have been an archive without a database), and so does one written so often that the copy is not done in ten minutes. The copy has the database's permissions. With `DB_URI` (PostgreSQL) the database is not in the archive, as before, which is now said.

The archive just made is always one of the seven. A run that fails or is killed leaves no partial archive under a backup's name: the archive is written under a working name and gets its own at the end, by a step that does not take the name from an archive of the same second (where the disk has no hard links, a second run in that same second can still put its archive in the place of the first).

- server: a server that cannot start ends with exit code 1 (P13: EXIT-0, SRV-15). It used to end with 0, or stay up without listening.
  - **What happened.** SES is run with `errorTrapping: 'report'` (`src/core/lockdown.js`): it listens for uncaught exceptions, prints them and lets the process go on. For a server that is starting, a refused setting (`[envs] ...`), an unreadable database or a world that failed to load was printed and then nothing: the process ran out of work and exited with code 0, which a supervisor or a deploy reads as a clean stop, or a database connection or a timer kept it alive and it stayed up without ever listening.

Until the server listens the process's exit code is 1, so a start-up that ends by itself says so. Before the world loads, any uncaught exception ends the process with 1. Every step the start-up awaits (the world directory, the asset store, the database and its migrations, the clean-up, loading the world, listening on the port) ends it with 1 when it fails. While the world loads, uncaught exceptions are printed and survived, as in a running server, whatever their origin: content in a world must not be able to keep its server from starting.

- server: the clean-up (`CLEAN`) has a stated contract, keeps what the world names by its file name whatever URL it is written in, deletes nothing when it cannot read what it must, and, with `ASSETS=local`, moves what it removes to a trash instead of unlinking it.
  - **The contract.** It keeps every store file whose name appears as a literal in the persisted world data or in the source of a store script reachable from that data, and deletes nothing when it cannot read something it must read. The code it follows is exactly: the store file a blueprint's script names, whatever its extension, and any `.js` store file named as a literal in that data or in code it follows. It cannot see, so such a file is removed: a name computed at run time (`'abc' + 'def.glb'`, a template, a hash) or written with JavaScript escapes (`'\x61bc.glb'`); code built at run time, that is code a script fetches or assembles and evaluates itself (`fetch` and `Function`), wherever it is hosted, the store included, and whatever that code names (no engine API runs another script: `world.load` takes models and avatars only, and an app's script is its blueprint's); references inside binary assets (a model's external image or buffer URI, which the loaders do not follow: models, avatars and emotes use their embedded data). Worlds that rely on any of these must run with `CLEAN=false`.
  - **What keeps a file.** Its name, found anywhere in apps, the blueprints that stay and collection blueprints (both as stored and as hydration loads them, with model and script cut at 2,048 characters), settings, user avatars, script storage (parsed, so JSON escapes are decoded; a copy set aside as unreadable is read as text), and the source of the code it follows, to a fixed point (a `.js` name the store listing leaves out, which holds content-hash names only, is asked of the store, at most 4,096 of them, and names nothing when there is no such file; one that is there but cannot be read stops the clean-up). The text is cut at every character a store name cannot hold, and a file is kept when a piece equals its name in any case, also percent-decoded (a run of up to 4,096 characters, at most 8 times), without dots, `_` or `-` at its ends, and with tabs, CR and LF inside it dropped (as the URL parser drops them), in one loop with the decoding (each pass drops them, then decodes once), so escapes and dropped controls in any order and position are undone, and what decoding brings in (`%09`, `%0D`, `%0A`) is dropped too. No URL is resolved for this, so a host, port, path prefix, `..`, query or CDN spelling cannot hide a name; ignoring case keeps what a case-insensitive file system loads from `asset://<NAME>`. A file named like a common word is kept whenever that word appears.

Database tables are read whole, as the world itself reads them when it starts; the read limit applies to each value, not to a table's total. The assets URL serves each store file's own bytes: a redirect, a rewrite or a cache in front of it that answers a file's URL with something else is not supported (the clean-up reads the store, the world loads what the URL serves). With the local store a removal is recoverable for CLEAN_TRASH_DAYS; with S3 it is not (turn on bucket versioning).
  - **The trash.** With `ASSETS=local`, removed files go to `<world>/assets-trash/<UTC date>/<name>` beside the assets directory (the same file system, so a rename; never served, never listed, on the disk the free-space check measures), one log line with the count and the folder. Folders at least `CLEAN_TRASH_DAYS` old by their UTC date (30 by default, so a file can go up to a day sooner than that after it was moved; `0` deletes at once and empties the trash, folders dated in the future included) are removed once discovery is complete, after anything trashed that is named again has come back from its newest copy that is still there (logged). If none of a named file's copies is there any more, that is logged and the trash is not purged that run. Nothing comes back while `ASSETS_BASE_URL` is not clean: the clean-up then stops before it looks. Before the purge, a kept file that is also trashed must still be in the store; if another process removed it, its trashed copy comes back, and if that fails the trash is not purged. With `ASSETS=s3` objects are deleted: turn on bucket versioning to keep a way back.
  - **Dry run.** `CLEAN=dryrun` changes nothing and names what would be removed (up to 50), what would come back from the trash, and which trash folders would be removed.
  - **No longer a stop.** A prop holding a non-string `url` (props accept any JSON) used to disable cleaning for the whole world; it is now just text.
  - **Cost.** Linear in the text: two walks over it without copying it, a percent-encoded run decoded at most 8 times and only up to 4,096 characters, every file read through one handle and counted up to the limit above, each place that holds an undecidable run recorded once (the log names the first 20). A world of 5,000 files and a 50 MB corpus is cleaned in under a second; 256 KB of nested encoding, or 40,000 places with such runs, stop it in a fraction of a second. The database tables are read whole (see Assumptions).

For any other contract the script gets `known: false`, the same answer as for a chain without an RPC, the node is not asked, and the server log names the contract once (the first 16 unlisted contracts of a server run, then one line saying there are more; never a player's address).
  - **The default.** With the variable not set, the list is one contract: OpenPay's license contract on Polygon, `137:0x1c652241Cc820Ce897F0d8D9351Df9AD8a0916cc`, so the shipped NFT door works as before. Setting the variable replaces that default (it does not add to it); setting it to nothing allows no contract. An entry in another form stops the server at start-up with an `[envs]` error instead of running with part of a list. The start-up log says which contracts are listed.
  - **What changes for a world.** A script that asks about any other contract (the `nft-gate.js` example set to an NFT of your own, for one) now gets `known: false` every time, and its sign says to try again, until the operator lists that contract and restarts the server.
  - **What this is not.** The list bounds which contracts are asked, not what they answer. Listing a contract trusts its `balanceOf` / `ownerOf` not to encode the owner: a listed contract that is upgradeable, or that its operator controls, can still return address bits, and nothing checks a listed contract again. A listed ERC-721 answers `ownerOf` for every token id, so a script that asks id by id learns which token a visitor holds and with it the wallet (one read per question against the shared budget, which slows this and does not stop it). A balance of a token with few holders can name a wallet. Every script in the world can ask about every listed contract. `getTokenBalance()` (the Solana balance, readable by client scripts) and the addresses that a tip announcement lets anyone find on chain are as they were.
  - **Docs.** `Player.md` has a section on what a script can learn from a holdings check; the comments of `nft-gate.js` and `nft-door.js`, the README and `.env.example` say the same.
- server: one visitor could get other players disconnected, and stall the server. Every packet shares one budget per connection (about a thousand small packets a second), which bounds the work of reading them, not what each sets off. A chat line is written to every connection: a thousand a second fill the write backlog of every recipient on a slow link within seconds, and a recipient whose backlog is full is closed. A name change is written to every connection and to the database: with SQLite each is a commit on the server's own thread.
  - **Budgets for what a person does by hand** (`src/core/extras/actionBudget.js`), per connection, counted by when the packet arrived: chat 1 a second (6 at once), a client script's chat 2 (10), the player's own name, avatar and session avatar 1 every 2 seconds (5), commands 2 (10), world settings and the spawn 5 (30), and kicks, mutes and changes of rank 2 (10), in a bucket of their own so that editing settings never leaves a moderator without one. A request that would be refused anyway (a player who is not here, a value the rules refuse, an admin's setting from a builder, an invalid transform for the spawn) is checked first and uses no budget. The admin code keeps its own brake and is not counted with commands; a granted `/admin` is counted as a change of rank. What goes over a budget is not carried out when it arrives:
    - a line of chat, a command, a spawn, a kick, a mute or a change of rank is dropped; the sender is told once per wait where a person can get there (chat, `/name`, commands, the spawn, ranks).
    - a name, avatar or session avatar is taken out of its packet, whose other fields (movement) go on, and the sender gets back the value the server keeps. A name the server shortened is corrected as before, whatever became of the avatar in the same packet.
    - a world setting is held, not dropped: the latest value of each setting from that connection is applied when the budget allows, and checked again then (the sender's rank may have changed). A number field sends a change per key repeat, about thirty a second with an arrow key held: the value the builder ends on is the one the world keeps, the sender's field is not set back under the key, and the others are told the first thirty and then at most five a second. Of the values of one setting held for several builders, only the one that came last can be applied: the others wait, and are let go when it is applied (or applied after all, on a later tick, if it goes first: its builder leaves, loses the rank, or it is refused when checked again). A held value refused when its turn comes (its builder lost the rank) is not applied, and its sender alone is told the value the world keeps. So between a value's arrival and its application no other value of that setting is applied, and the pane of a builder whose values are held ends on the value the world keeps. Not covered, as before the budgets: a value sent by someone who is no longer a builder is refused as it comes, without an answer; and two changes crossing in flight, where the builder whose change reached the server second is told the first one and, when that message arrives after its own change, shows it while the world keeps its own. Nothing is held for a connection that is gone, or once the server stops.
  - **A chat line cannot close a recipient.** Player and app chat are written as skippable: a connection whose write backlog is high misses the line instead of being closed for it.
  - **An effect is seven fields.** A player's effect (`ef`) was any JSON up to 8 KB, written to everyone with each update; it is `anchorId`, `emote`, `snare`, `freeze`, `turn`, `duration` and `cancellable`, each a short primitive, and at most 2 KB in all (the UTF-8 bytes of its JSON; what the engine builds is under 1 KB in ASCII). One with another field, or over that size, is not an effect.
  - **Nothing new, nothing done.** A name or avatar equal to the one the player has is not told to anyone or stored again. Each change that is taken is one write to the database, as before: the identity budget is what bounds how many there are.
  - **What this is not.** The budgets are per connection: several connections multiply them, and the limits on connections per address are what bounds that. Movement, building and script events are not budgeted here (an honest client sends them at frame rate, and a dropped one leaves players out of step): a flood of those still reaches everyone. Writes of a user's row (name, avatar, rank) are as they were: one UPDATE for each change, not ordered or merged per user, and a player who joins again reads the row as it is at that moment. The spawn is not merged either: each change of it that the budget lets through is written, also one that a later change replaced while it waited for its turn. Chat is limited in rate, not in content.
- server: wrong admin codes cost nothing. `/admin <code>` compared with `===`, and a wrong code was neither counted, delayed, answered nor logged, at up to about a thousand attempts a second per connection: a short code could be found by trying, unnoticed. Codes are now compared in constant time (SHA-256 digests, `timingSafeEqual`) and wrong ones are slowed down per user id, per address and per wider network, with one summary line in the log a minute after the first wrong code (never the code, never an address). This is a brake, not a wall: every new connection is a new user id, so only addresses hold a guesser, at about 1,400 guesses a day from one IPv4 address and 8,600 from one IPv6 /48. A six-digit code does not hold for long against that; 16 random characters do. Someone on an admin's own address can keep that address waiting; a stored admin rank needs no code.
- server: one visitor could run a world's server scripts about a thousand times a second. A script event from a client (`app.send` in a browser) runs the app's server listener when it arrives, and only the budget every packet shares bounded how many: about a thousand small packets a second per connection. Script events now have a budget of their own, per connection (`event` in `src/core/extras/actionBudget.js`): 320 a second, up to 1,280 at once after a quiet time, counted by when the packet arrived and shared by all the apps the connection sends to. It is asked only for an event the app takes: one its script has a listener for, or one the app keeps while it builds (a builder's event for the next version of a blueprint included). An event that is neither kept nor listened for uses none: one for an app that is not there, of a version the app refuses, with a name the running script does not listen for, or for an app whose script has crashed. An event over the budget is dropped, not held or delayed: it is counted with the app's other dropped events and logged once per app and once per connection. Nobody is closed, and the sending script is not told (`app.send` has returned `true`). The browser keeps the same count on its own clock, of every event it sends, and warns once in the console that events may be dropped. A script that sends an event every frame sends 60 to 240 a second, depending on the display; two apps doing so at 144 Hz send 288, which passes. A connection whose scripts send more than 320 a second for longer than the burst lasts loses the excess: `docs/scripting/app/App.md` said "Send deltas, not full state, at high rates" and now gives the numbers and says to send at a fixed rate. What this is not: a limit per person (each connection has its own budget, and the connection limits allow 8 per address); a bound on large events (one of 6 KiB or more is bounded below 320 a second by the budget every packet shares); a bound on what a listener does with 320 events a second, or on what scripts send. Movement and building are not budgeted, as before.
- server: any visitor could make every other visitor's browser download and parse a file from any host. A player's session avatar and emote took any `http(s)` URL from any connection (`sessionAvatar` in a player's own update or the `avatar` parameter of the `/ws` URL; the emote in `e`), with the Custom Avatars setting on or off, and with it on, the stored avatar took one too and kept it for every later visit. Each client that saw the player fetched the file (up to 64 MiB for an avatar, 32 MiB for an emote): the sender learned every viewer's address and got their parser and their bandwidth. Now a URL outside the world (`isExternalUrl`: anything that, as the loaders read and resolve it, is not requested from the world's own store: an `asset://…` file, or an address under the store's own URL) is taken from a player only while the player is a builder, or when it is the very URL a server script chose for that player (the session avatar a script set, one of the last 16 emotes a script's effects carried). A refused emote becomes none; a refused session avatar is dropped and the sender's own view is set back. What this does not change: builders, and server scripts, can still name any URL; with Custom Avatars on a visitor can still upload a VRM of their own making, which everyone parses (size-capped, served from the world's store, with no references outside its own file). A server script that passes on a URL a visitor supplied gives that visitor the old reach.
- server: one visitor could get every player on a slower link disconnected by moving. What a client changes on its own player (position, facing, emote, effect) was written to every other connection as each packet was handled, and only the budget every packet shares bounded how many: about a thousand a second of 1.6 KB each from one connection, which is about 1.7 MB a second to each recipient (2.7 MB a second as the write backlog counts it, with 1 KiB for each write). A recipient that could not take about 14 Mbit/s fell behind until its backlog reached 1 MiB and was closed, at 8 Mbit/s within about a second, and again when it came back.
  - **A player's own changes are merged per tick** (`src/core/extras/pendingChanges.js`). The server applies each change when its packet is handled, as before, and tells the others once, when the tick's packets have been handled: one packet per player, with the latest value of each field its client changed in that tick (a teleport stays a teleport when the player moved again in the tick). So per connection, at most one own-player packet per server tick is written to each other connection: 30 a second of at most about 3.8 KB of packet (every field at its limit in three-byte characters, since the limits on urls and names count characters; about 2.7 KB in ASCII), which is about 114 KB a second (about 145 KB as the backlog counts it, with 1 KiB for each write; the framing of the connection is not counted in either), and up to about 2.5 KB more in a tick in which the identity budget lets a name or an avatar through. A client sends its movement 8 times a second, so normally one change in a tick, told as it came; two that arrive in one tick are told as one.
  - **What the others see differently.** The packet is written at the end of the tick's packets, not when its own packet was handled: a delay of less than a tick (33 ms), and a line of chat sent after a step in the same tick now arrives before the step. The values in between are not sent: of a client script that teleports its player or sets an effect on every frame the others get what each tick ended on, 30 a second, and an effect set and ended within one tick is never shown to them (`docs/scripting/world/Player.md` says so).
  - **What the server itself tells everyone about a player is not undone by that player's earlier change of the same tick.** An effect, a session avatar or health set by a server script, `/name`, a change of rank and the urls a former builder may no longer show are written at once, as before; their fields are taken out of what is pending for that player, which would otherwise be written after them and set the others back to the older value. A script's write that was refused (the tick's budget for script writes is used up) reached nobody and takes nothing out. A recipient that a script's write skipped (its backlog is over 512 KiB) misses the client's value of that field as well, and stays on an older one until the field changes again. Nothing is told about a player after its removal, nothing is kept from one tick to the next, and a server that is stopping lets go unsent what it had not yet told.
  - **What this is not.** The bound is per connection, not per person: several connections multiply it (8 per address by the connection limits), and it is a bound on what one connection makes the server write, not a promise to a slow recipient: enough players moving at once still fill a link that cannot carry them. The server still applies every packet as it arrives. **Builders are not bounded**: changes to apps and blueprints are written as they come, as before, and one builder can still have about 1.2 MB a second written to every recipient by adding and removing an app in a loop (146 pairs a second of 8.3 KB), or about 2 MB a second with app state over nine or more apps, or with blueprint versions (34 a second of 60 KB); a recipient below about 12 to 16 Mbit/s is closed, again and again. Only a budget of bytes per source would bound that, and there is none. The entry above on budgets for what a person does by hand says movement is not budgeted: it still is not (none of it is refused); it is merged.
- server: ten log lines printed an id or a setting's name from a packet with only its length cut, so a line break in it started a line of the sender's making in the server's log. They print it as `previewValue` does: quoted, printable characters only.
- scripts: a node's `cursor` could be an image (`url(...)`). The value is the cursor style of the page's body while the pointer is over the node, so it also showed over the engine's own interface: a script's image could stand in for the pointer over the wallet, tip and confirmation dialogs, drawn away from where a click lands. Only CSS cursor keywords are passed on (`src/core/extras/cursorKeyword.js`), in the node's setter and again where the style is written. - moderation: a kick kept nobody out and did not end what the kicked player said or showed. The server closed the world's connection and nothing more: the player reloaded and was back as the same user with the same rank, and since the voice room is a connection of its own that no client ever closed, everyone who already heard a kicked (or simply disconnected) player kept hearing them, at their last position, and kept seeing their screen share.
  - **Leaving the world ends voice.** A client leaves the voice room when it is kicked or loses the world's connection, and every client drops a player's voice and screen share when that player leaves the world, whatever the voice server says.
  - **A kick holds for a while** (`src/server/kickList.js`). The kicked user id is refused for `KICK_MINUTES` (default 10, 0 to 1440; 0 only disconnects), with the kick code `kicked`, before anything is added or announced, also when the kick lands while the same user is reconnecting. It is a delay, not a ban: user ids are free, and a player who clears their browser's storage is a new user. `KICK_BY_ADDRESS=true` (off by default) makes new users from the kicked connection's address wait too: only an admin's kick makes such an entry, never for an address that could not be read, and it refuses only connections without a valid session token; everyone new behind that address waits with them. Nothing is stored: a restart forgets the list. It holds at most 4,096 user ids and 4,096 addresses: a kick past that lets the oldest back in before its minutes are over.
  - **Who may kick and mute.** `kick` and `mute` named any entity: with an app's id the rank comparison passed (an app has no rank), so any visitor could broadcast `mute` packets, with any value, as often as they liked. The target is now a player, the value a boolean, and the sender must outrank the target by the rank the players pane compares (the session's rank, a token's grant included, and the world's). In a world where everyone is an admin (no admin code) nobody outranks anybody: nobody kicks or mutes there, as the pane already showed.
  - **A mute covers the screen share.** A muted player's share is hidden on every client and shown again when the mute is lifted. The list of muted users holds at most 1,024 ids (at the limit the longest-muted absent player is unmuted, said to everyone); a muted player who comes back is said to be muted again, since a join snapshot made under size pressure leaves absent players' mutes out.
  - **Voice token.** It no longer allows data messages or a screen share's audio (nothing sends or plays either).

A muted player's client still sends its microphone to the voice server, and a modified client hears every voice in the world at any distance: the voice server sends every track to everyone. A modified client that was kicked can stay in the voice room and listen for as long as it stays connected, since the voice server keeps sending a connected client fresh tokens; six hours is only how long the token it was given when it joined lets it connect again. Nothing it sends is played, as it is nobody's player. The server makes no calls to the voice server. Any participant can show a screen share on any video node with a `screenId`; mute and kick are the tools against that.

- server: the pages had no security headers at all. The world page asks for wallet signatures and sends tips, and any other site could show it in a frame under its own page and have a visitor click through it.
  - **Framing.** The pages (the world page, and the static pages on every answer, a 304 to a browser revalidating its copy included) say `Content-Security-Policy: frame-ancestors 'none'; base-uri 'none'; object-src 'none'; form-action 'self'` and `X-Frame-Options: DENY`: no other site can frame the page, and markup that got into it cannot change where relative URLs load from, embed a plugin or post a form to another site. Nothing on the pages uses what these forbid.
  - **A second copy of the world page.** `/index.html` was served as the built file, a working copy of the world page outside the route that serves `/`. Both names give the same page now.
  - **Uploaded scripts are text.** A `.js` file of the store was served from the page's own origin as `text/javascript`: its `sandbox` and download headers did not stop a `<script src>` or an import from running it with the page's rights, nor a worker in Chromium and WebKit (an engine that applies `sandbox` to a worker refused that one already). With `ASSETS=s3` the type is stored with each object when the object is written: the built-in assets are written again at every start and get the new type, but a script uploaded before keeps `text/javascript` until its object's metadata is changed in the bucket or the object is replaced there (and a CDN in front may need invalidating). - scripts: script code reached while an app's nodes unmount (a method a script defined on a node's `matrixWorld`, which taking a linked instance out reads) could make what earlier teardown stages had already released: a player handle and effect (the closed player registry was dropped and made again), a voice modifier, a world-space node or video that stayed mounted (and changeable) after the app was gone, or a child added under the unmounting root. Taking a linked instance out keeps the Model's list and the octree right even if reading the moved instance's matrix throws.
- scripts: script code that runs in the middle of an engine operation and ends its app (removes or rebuilds it) no longer leaves the interrupted operation's resource behind. Such code could be reached in three ways, all closed:
  - **Engine math objects.** A script could define an accessor or a method on an engine-owned vector, quaternion or matrix it holds (a node's `matrixWorld`, which taking a linked instance out reads; a node's `position`, which an activation reads), and the engine then ran it mid-operation; it could also replace such an object's `_onChangeCallback`, which the engine calls on every change (inside a physics step, say), or write an object straight into a component (`_x`). Those objects are now sealed where they are made (nodes, joints, UI offsets, control camera, poses and sticks, skinned-mesh bones; a particles node keeps engine copies of the vectors it is given), their change callbacks are fixed once wired, and an object stored as a component becomes `NaN` without its `valueOf` being called. A node's own four transform objects, which scripts write all the time, are handed out as they are and read by the engine only through a guard (`Node.guardTransform`: a component that is not a number is read by the engine's number rule, `extras/engineNumber.js`, an object as NaN without being converted) wherever it consumes them: the matrix composition, the rotation/quaternion change callbacks, a collider's local pose, a screen-space UI, the Animation system, an app's network interpolation, the builder (also its grab and gizmo targets, three's own objects) and the apps list. The copy family itself (`copy`, `set`, `fromArray` and the `setFrom` copies of our Vector3, Quaternion and Euler, whose prototypes three's own objects share for the latter two) applies the rule to what it reads before the change callback runs, and the network interpolators are made of these classes (they were three's plain Vector3, whose `copy` kept a planted object for the next frame's arithmetic). Everything else (matrices and their elements, joint, UI, control, bone and particles vectors) is handed out as a view that keeps numbers in its fields (the engine keeps using the objects themselves; see Changed). A Symbol or a BigInt in a matrix entry made the stage's instance read throw (a Float64Array cannot hold one) out of `Stage.update`, stopping every app's linked meshes: views keep numbers, and the read itself takes each entry that is not a number as NaN.
  - **Arguments.** A getter, `toString` or `valueOf` in what a script passes could end the run after the call had been admitted: `app.control({ get onRelease() {…} })` left a control and a hidden reticle, `applyEffect({ get freeze() {…} })` an effect, `app.on({ toString() {…} }, fn)` and `world.on(…)` a listener, `app.configure(() => {…})` fields. Every handle method now reads its arguments first (into plain values), then checks that the run that called it is still current and its stage has not begun, and only then makes anything. The run is the one current when the method was entered; it is never read again from the app (whose next run, or a removed app's fresh hook, would pass). The calls that act at once read their arguments first and check the run before acting: `world.set` (the value is read once, as JSON, and the store gets the host's copy), `app.send`/`app.sendTo` (the data is read once into a host copy by the engine's own reader, before the packer sees it; for what scripts ordinarily send the copy packs to the bytes the data itself packed to, a subclass of `Map`, `Set` or a typed array is now sent as the built-in with its contents, and data of more than 524,288 values, which no packet could hold, is refused with a `RangeError` instead of being read until memory ran out; the packer used to read it, and a getter in it that sent another message entered the packer a second time, which put one message's bytes in the other, could leave the inner one unreadable, and could make the next message of anyone throw. Now both messages go out whole, the inner one first, and a pack begun inside another is refused), `player.teleport`/`push`, and `damage`/`heal`, whose amount follows the number rule (an object is not converted and changes nothing); `setSessionAvatar` and `screenshare` take strings only.
  - **Engine callbacks inside an operation.** A commit that rebuilds (unmount, mount) mounted again after its unmount had retired the app; `applyEffect` installed its effect after the replaced effect's `onEnd` (this app's or another's) retired it; a lookup that evicted a handle (its `onEnd` rebuilt the app) inserted the new handle into the old registry. Each now checks the same run again after the callback and before it publishes, and takes back what it made (a mount, a world-space placement) when the run ended meanwhile.
  - **Also.** A build asked for during a teardown takes its place in the build order when it is asked for, so a newer build supersedes it, and its failure no longer clears a newer build's state. A crash tears its run down at once, through the same teardown as a removal, whether or not the crash block can be shown (a crash block that failed to load used to keep the run's nodes, control, voice modifier, listeners, request and object URLs). `getPlayers()` is refused from the player stage on also when nobody is in the world. Instance matrices read inside one another each use their own array. Trees returned by `world.load()` and model nodes below an inactive node belong to the run (their handles stop with it). A voice level the voice system refuses (`setVoiceLevel('no such level')`) used to drop the handle's record of its current modifier, which then outlived the app. An audio node removed while its start waited for the audio unlock (a page nobody had clicked yet) threw when stopping the never-started source and left its gain connected to the output (and the node unable to play again); a video left its gain connected to the music output on every unmount. A crash also tears its run down when a blueprint change asked for a build in the same task (that build tears the current run down only once its model has loaded, so a model that never loads or fails left the crashed run's control, listeners, requests and nodes behind), and a build whose crash block cannot be loaded ends, reported, instead of rejecting where nobody waits on it.
  - **Values kept for later.** A setter that accepted a boxed primitive or a Proxy posing as a number or string (the lodash checks) kept it, and host code converted it later, in the middle of a commit, a mount (a sky, an image, a UI's layout, a video's audio path, a prim's emissive), a WebIDL call or another app's frame (a controller's `tag` reaches other apps' contact callbacks). Node setters now keep primitives only (`extras/scriptPrimitives.js`), the arrays a node keeps are frozen copies of primitives, an effect keeps primitive fields only, and an LOD distance is a number.
  - **The sweep.** `test/teardownSweep.test.js` and `test/teardownNodeTypes.test.js` drive real apps in real compartments through every callback point, every allocating API, every argument trap and every node type that mounts in Node (with real content), and compare a footprint of every registry the run can reach (nodes, scene, instances, octree, anchors, LODs, actions, snaps, nametags, particles, skies, video instances, UI canvases, controls, reticle, HUD, pointer, effects, voice modifiers, listeners, timers, hot, requests, sounds, object URLs, fields) with an empty one.

The server is never the stricter one: it draws nothing, so the morph-target textures a client is charged for are not charged to it. With a budget the parser decodes a file's `data:` buffers itself, so a `.gltf` with an embedded buffer now loads on the server (it used to fail: three's file loader needs a browser's `ProgressEvent`), also when the scheme is written `DATA:`. The vendored parser no longer starts loading a meshopt-compressed buffer it will not use (an optional extension without a decoder): a refusal of that buffer surfaced as an unhandled rejection.
  - **Before deploying to an existing world.** `npm run models:check -- <world>/assets` (or `node scripts/check-models.mjs [--max-texture-size=<n>] <files or directories>`) takes every `.glb`, `.gltf` and `.vrm` through a client's steps and lists what is refused, with the reason, and how much of the limits each accepted file uses. It only reads the files and requests nothing they name. A file refused by the check before parsing fails to load in every client and on the server; one refused during the parse for its morph-target textures depends on the client (that charge grows with the renderer's largest texture size, which the script takes at its largest unless told one), and the server does not refuse it.
- client: an avatar, emote or model that another user supplies can no longer stop rendering for the people who see it.

The bones the engine needs (hips, head, upper arms) are now checked while the file loads, and so is the skeleton it drives (the first skinned mesh's: it must have bones, all of them in the scene, a root bone with a parent, and the hips and head). Optional bones are skipped where they are used.

A failed emote is reported and forgotten instead of leaving an unhandled rejection. An emote file without an animation fails its load with a reason. - client: the loader checks what it downloads.
  - **Status.** A 404 or 5xx page is a failed load. It used to be parsed as the model, image or script.
  - **Size.** A download from outside the world's store stops at a limit for its kind (2 MiB scripts, 32 MiB images and emotes, 64 MiB models, avatars, audio and HDRs), whether the size is declared, real or endless. In the world's own store the limit is the upload limit (`PUBLIC_MAX_UPLOAD_SIZE`), or the kind's limit where that is larger, so a 3 MiB script accepted at upload also loads after a reload. The same limit applies to a file the loader already holds and to a file just picked for upload.
  - **Transfers.** Every refused transfer (an error status, a size over the limit) is aborted. A download that receives nothing for 30 s, or is still running after 120 s, is abandoned. A response without a readable stream is read only when it states a length within the limit.
  - **Pixels.** Images, textures and HDRs above 36 megapixels are refused. An HDR is refused from its header, before the parser allocates its pixels (a file of a few bytes could declare a billion rows). The textures inside a model, avatar or emote are held to the same budget; a file with a larger one fails its load and what was decoded from it is released.

  - **Limits inside the parser.** What they bound: what the vendored parser itself allocates, creates and decodes, and the work it and the check before it do, each charged before it happens; and the time they take. The limits are set from VRoid's sample avatars (VRoid Studio's AvatarSample_A and B, five more VRM 0 and VRM 1 samples, 6 to 20 MB): each meter has at least three times what the largest of them needs. Models, avatars and emotes are parsed by the vendored GLTFLoader (`src/core/libs/gltfloader/GLTFLoader.js`, its `COO_BUDGET` and `COO_WORK` sites), which charges a per-file budget from the real objects at that moment rather than from what the file declares. Bytes: every array it creates or copies (the GLB's binary chunk, each bufferView, accessors without data, sparse accessors, which copy the whole array, strip and fan conversions, which copy the geometry, instancing matrices, converted animation values, `extras` and each clone's copy of them, each object's name and each track's, the morph-target texture the renderer will build), up to 320 MiB beyond twice the file's own size. The morph-target texture is three.js's own allocation: one per geometry, so a VRoid face of ten primitives sharing their vertices and 56 targets is ten textures, padded to rows of the renderer's maximum texture size (the largest any size would take while that is not known). That is most of an avatar's cost: AvatarSample_A is charged 110.8 MB for its 15.1 MB, 73.4 MB of it morph textures (36.8 MB where the maximum is 16384); the bundled avatar 17.8 MB. Objects, per file and counting every clone: 64 scenes, 1024 cameras, lights and animations, 65,536 nodes, primitives, mesh instances, channels and tracks, 16,384 meshes, materials and textures, 262,144 joints and morph influences. Work, up to 2^26 steps plus one per byte of the file, charged by reference: each use of an accessor at its declared size (elements x components) wherever the parser resolves it, for each mesh made of a primitive (50 skinned primitives on one shared 2000-vertex geometry had their weights normalised 100,000 times for 270 steps), each animation track and each instanced mesh; each object placed under a parent at what three.js goes through to take it from its old one (a scene listing 1000 roots twice shifted 999,000 entries for one step a root), emptying a group at its splices; each clone at what it copies (its userData, its morph influences; a material's variant also each texture in a ShaderMaterial's uniforms, which three.js clones with it); and each loop or walk the document sizes (sparse entries, the subtree each morph-weight channel walks, the scene walks, the entries of each list it goes through). The check before parsing is charged to the same budget (a step per entry it goes through) and looks at the same clock; it is linear in the document. AvatarSample_B takes 20.1 million steps, the bundled avatar 1,035,591, an emote 58,170 to 122,087 (the check and the parse as the client runs them, charged to one budget, with the VRM plugin registered as for every file; the check alone is 53,516 of the avatar's and 53,750 to 66,470 of an emote's). A copy of userData (three.js makes one, as JSON, with every clone of an object, a material or a texture) is charged at an estimate of what it holds, not its text: 2 bytes a character, 24 more per value in a list, 56 more per property and 96 more per list or object, outside strings. Measured, not proven: on V8 (Node 24), over 52 shapes of up to 64 KiB, the largest held ÷ charged was 1.01 (a long string of two-byte characters), objects of many short keys at most 0.95 (one with 5,560 two-character keys held 1.40 times its charge at 24 bytes a property), a list of empty objects 0.51 (11.7 times the two bytes a character charged before: a reviewer's 68 clones within the work limit held 1.6 GB, 135 MB charged). A texture whose image is a data: URI is cached by the image, not by the URI (the parser built and looked up a key of the whole URI for every texture: 2000 textures on one 8 MB URI took 2.4 s, and now 0.7 s, the image's one decode). A data: URI image that does not decode is refused like any image that is not one, so the parse fails (it had loaded, without the texture); the empty placeholder a refused texture gets in its material (three-vrm's MToon plugin never awaits the promise it wraps the texture in) is put in only once the parse has failed, and any other texture error goes on as it did. Time: the check and the parse are refused at the first charge after 10 s on a monotonic clock (the bundled avatar's take about 3 ms in Node on a desktop, the VRoid samples 8 to 44 ms). A file of a few hundred bytes that declares a billion vertices is refused at its mesh's charge, before anything is allocated. The parser asserts on the real arrays what three.js relies on: an animation track's times one per keyframe and a whole number of values per keyframe from arrays of just the accessors' own elements, as many as the document declares (a sparse accessor on an interleaved view copies all of them), a skinned primitive's joints and weights one per vertex, a skin's inverse bind matrices one per joint, sparse indices strictly increasing inside their accessor (the specification's rules; on the server too). Loops whose length comes from the document go over real lists only, and morph weights no further than the targets. A test reads the vendored file's syntax and fails on any `new` (but a thrown one), spread, loop or call without a marker of its own, a comment starting with the marker word, and on a function calling itself without one for its depth; the calls it lets through are this file's own functions and an allow-list of cheap callees, each with its reason. The allow-list is by name, not by binding: a library function assigned to an allowed name (`const resolve = structuredClone`) or handed to an allowed method as its callback (`.then(structuredClone)`) passes, as does an allowed method name on another kind of object (`text.normalize()`); and the test does not see recursion through two functions, through a callback or through another name for the parser, tagged templates, copies by rest destructuring, or the join of a list converted to a string (`'' + list`, a template). None of these is in the vendored file (a reviewer's probe inserted each one); they are found by reading it. A marker on a call into three.js or three-vrm is a claim about that library's cost, which the test cannot see. What the limits do not cover: cost inside three.js and three-vrm that is proportional to what is charged is covered by those charges; cost there that multiplies in ways the charges do not capture is not proven absent. The time limit turns it into a refusal at the next charge, but cannot interrupt one long loop inside a library (see Still open).
  - **Before the parser.** The container and the structure are checked first (`src/core/extras/gltfLimits.js`): GLB chunk lengths, a JSON chunk of at most 16 MiB that nests at most 64 deep (a .gltf's JSON too, counted without the payloads of its buffers' and images' `data:` URIs, which are data: it was held to nothing, and a 20 MB one passed; a `uri` anywhere else is a string like any other, capped as one), every index a non-negative whole number in range (a string index is refused; UniVRM's -1 for "none" is accepted in the VRM 0 fields three-vrm reads as absent, such as a spring bone group's center, but not as a human bone's node, which three-vrm looked up: a TypeError), every list a real list of at most 2^20 entries (and at most 1024 morph targets a primitive), a node hierarchy that is a tree at most 256 deep (a chain of thousands overflowed the parser's stack), no glTF 1.0 `animation.parameters` or `buffer.type` (the parser still honours both), required extensions this client can load, each extension named once, and a scene's roots each listed once and a child of no node (the parser re-parented a root it met again, a search and a splice of its old parent's children each time; such a scene never loaded as written). Strings are short by rule, because the parser and three-vrm keep, compare, concatenate, sanitise or key on them once per object: every string and every key they read (a name, a kind, an extension's, an attribute's, a bone's or an expression's name) is at most 1024 characters, a URI that is not a data: URI at most 2048, and the asset's and the VRM meta's text, read once, at most 16,384 (the longest in the bundled files and VRoid's seven samples: 59, a key 31, the text 51). A mesh name of a million characters was sanitised and kept for each of 1000 primitives, stopped only by the clock. A data: URI is the data, its bytes charged where they are decoded, by one decoder, once: the bytes sized and charged are the bytes the parser uses. A `data:` image is decoded by the budget, its first 256 KiB first (an image refused from its header costs only them), then, accepted, whole, straight into an array of its size, each array charged before it is made, its header read from those very bytes; the parser hands that array to the image decoder in a Blob, through the same object URL (revoked however the load ends) as an image inside the file, and never fetches the URL. The decode went through an `atob` string and a list of numbers, about 20 times the URI, and charged nothing (300 to 380 MB for a 15 MB URI). Without a budget (the server) both are fetched as upstream. The `data:` scheme is recognised in any case, as RFC 3986 says, by one test that the check, the parser, the budget and the client's URL filter share (an upper-case `DATA:` was a relative URI to the check, data to the parser and the budget, and refused by the filter). A value they treat as a string must be one (a material's name given as a list was joined into a string for every outline three-vrm cloned from it), a sampler's filters and wrapping and an accessor's component type are numbers, and an image's `mimeType` is one of a fixed list, image/png, image/jpeg, image/webp, image/ktx2 or image/avif (the last two the types of the images KHR_texture_basisu and EXT_texture_avif name; an optional KTX2 or AVIF image is skipped for its fallback): each texture's userData keeps it, and three-vrm copied a 100,000-character one into nine slots of every outline (180 MB from a 0.11 MB file, 0.88 MB counted). Strings inside extras, and inside extensions nothing here reads, are not names: they are within those sizes. A URI has no line break (`\n`, `\r`, U+2028, U+2029), and a `data:` URI has the shape `data:[<type>/<subtype>][;<name>=<value>]...[;base64],<payload>`, the part before the comma a name (at most 1024 characters): base64 broken into lines, a space before `base64` (`data:image/png; base64,…`, which some fetches accept) and base64 with %-escapes (which browsers decode first) are refused, and so is a payload that is not base64 with a raw control character, a space, a character past ASCII or a `#` (the forms on which a URL parser and a decoder disagree). A texture has an image this client decodes, its source or a WebP one: an optional KTX2 or AVIF texture without a fallback source failed in the parser with a TypeError. A root shared by several scenes is valid glTF and loads: it ends in the last, each move charged. Draco and meshopt compression are accepted when optional (the parser reads the fallback data; an optional Draco extension without a decoder used to fail the load). Accessors must be what the parser and three.js assume of them: an animation sampler's times one float a keyframe and its values one per keyframe (three for CUBICSPLINE, one per morph target for weights) of the path's type, neither interleaved, so a track's value size is a whole number (7 values for 2 CUBICSPLINE keyframes, a value size of 3.5, made three's interpolant loop forever, and so did times at a byteStride of 8, which reached the track as twice the floats); a skin's inverse bind matrices a float 4x4 matrix per joint, not interleaved; a primitive's attributes, and its morph targets, of one count, its indices unsigned and not interleaved, and every primitive of a mesh with as many targets; instancing attributes of one count, at most 16 on a node (the parser goes through each for every primitive); every bufferView within its buffer (its byteLength, and the bytes the buffer really holds: a `data:` buffer's decoded data, the GLB's binary chunk; past them the parser threw "Invalid typed array length"), every accessor at least one element, within its bufferView, strides and offsets by the specification's rules, and sparse entries no more than its elements. three-vrm, which is not vendored, is bounded by its work counted in the units its plugins iterate. Counted: expressions, bind objects, the primitives they refer to, the steps they take (each morph bind walks its node's subtree, each VRM 0 material value the scene), spring joints and colliders, joints x the colliders of their groups, sorting the joints, first person (every node, the subtree of each with a mesh, the annotations), node constraints, the draws MToon outlines add (two per outlined mesh on a geometry the parser shares between meshes with the same primitive: 300 such meshes drew 180,000 groups), and what the outline material three-vrm clones for each outlined primitive copies, up to 16 MiB: the material's userData (its extras and the extensions the parser does not handle), and for each of MToon's 10 texture slots the largest texture userData in the file, an image's extras and its mimeType (which image a slot holds is not modelled: an extension's source, the parser's texture cache and VRM 0's slots can each resolve it to another), each copy at that estimate (50 outlined primitives on one material with 1000 small objects in its extras made 50 copies of them, about 1 MB, while nothing was charged); and what an expression's texture-transform binds copy, up to 16 MiB: each clones every texture slot of each material it binds (up to 8, a MeshStandardMaterial's), once per mesh the material is on (VRM 1) or per material named and its outline copy (VRM 0).   - **Transfers at once.** At most 8 downloads from the world's store and 4 from other hosts run at once (each pool on its own, so slow hosts cannot hold up the world's assets); the others wait without a connection, and their deadlines start when they do. That is the bound on bytes in flight: each transfer stays within its kind's limit (a stated length over it is refused before reading, a body that grows past it is cut off), so downloads from other hosts hold at most 4 x 64 MiB = 256 MiB at the very worst, and the world's own at most 8 times the upload limit (or the kind's limit, if larger). At most 256 loads from other hosts may wait or run; past that a new one fails at once and is not kept. The world's own loads are not capped in number.
  - **Late downloads.** A transfer is filed from the moment it is asked for: a file picked or set for its URL while it waits for a slot or downloads is the one kept (and, once the slot is granted, the one used), and a download that finishes after `destroy()` writes nothing. `destroy()` aborts the downloads in progress and fails the waiting ones; a request asked for just before it fails without taking a slot in the next lifecycle.
  - **Avatar skeleton.** The bone taken out of the scene as the skeleton's root is the one above the hips, not the first joint the file lists. With the joints listed head first, the head was taken out and the hips were moved twice (a probe placed at X = 10 reported the hips at X = 20). An avatar whose head is not below that root is refused; stray bones outside it are accepted.
  - **Images without a size.** An image or texture whose intrinsic width or height is zero fails its load.
  - **Image sizes from headers.** The size of a PNG, JPEG or WebP is read from its header before anything decodes it, so a header of a few dozen bytes declaring 100000 x 100000 no longer reaches the decoder. The reader walks the PNG chunks to the image data, the JPEG markers to the first scan and the WebP chunks; a file that is inconsistent (a second IHDR, an APNG frame outside the image, a second JPEG frame header in front of the real one, which decoders read differently, a WebP image or frame that does not match its canvas) is refused everywhere as malformed. Stand-alone images and textures (the world's store and other hosts, loaded or just picked) are refused there when over 36 megapixels, without a size or malformed. Other formats (GIF, AVIF, SVG, BMP) go to the browser's decoder as before and are checked once decoded. Inside a model, avatar or emote the parser sizes each image at the place it is about to decode it, so what is charged is what is decoded: images the parser shares (textures on one bufferView with one sampler) are one decode, and an image only a KTX2 texture would use is not decoded at all. A file's decodes together may have at most 256 Mi pixels (sixteen 4096 x 4096 textures, about 1 GiB decoded); the bundled avatar decodes 4 Mi. An embedded image named by a `blob:` URL is refused. The decoded size is still checked afterwards, on both paths.
  - **Memory.** Files and results for URLs outside the world's store are kept up to a bound, least recently used first out; a load still in progress is not dropped, and a dropped or replaced one no longer writes its result back. Video loads are kept under the same bound. A decoded image releases its object URL, which used to keep the downloaded bytes alive for the life of the page. Bytes that do not decode are not kept, so the next load downloads them again.
  - **Files just picked.** A file inserted before its upload (the file fields, a dropped model or avatar, `.hyp` import) is checked and decoded as a download is: a broken image fails instead of staying pending, and a failure is not kept.
- server: a builder could make the world impossible to join, and keep it that way across restarts. App entity ids had no length limit and nothing bounded how much the apps add to the join snapshot, so 36 `entityAdded` packets with 30,000-character ids (or about 7,300 ordinary ones) pushed the snapshot over its 1 MiB cap; every later join then failed, admins included, until the database was edited by hand.
  - **Ids.** A new app's id is 1 to 64 characters of `A-Z a-z 0-9 _ -` (what the client generates fits) and cannot be the id of any user this world knows, present or away (players and apps share one id space, and an app holding an absent user's id would have collided with that user's next join). The server keeps the user ids in memory for that (about 60 bytes each: 6 MB for 100,000 users). It refuses a second entity with an id that already exists, and a `blueprintAdded` for an id that already exists (changing a blueprint takes `blueprintModified` and its version rule).
  - **An app that already holds a user's id** (stored before this rule) moves to a new id when that user joins: it is removed and added again under the new id with its blueprint, transform, pinned flag and state (state a script made unreadable becomes `{}`), broadcast, and logged once with both ids. The player joins as usual. The move cannot lose the app: the new row and the old row's removal are written in one transaction, so a stop leaves the app under one id; a failing app teardown does not stop it. (The server's database is always knex on SQLite or Postgres, which has transactions. Only a stand-in database without them, in tests, writes the new row first and can be left with the app under both ids, which nothing merges at start-up.)
  - **World budget.** Blueprints, app entities, settings and collections together may take 768 KiB of the join snapshot. A change that would go past that is refused the way an over-budget blueprint already was (the sender's copy is reverted, one log line per connection), whether it comes from a client, a server script or the AI, and a settings change too. A blueprint change that rebuilds its apps counts the client-set app state it empties. The 512 KiB blueprint budget still applies.
  - **The rest fits by construction.** What no budget tracks is dropped from a snapshot that does not fit, one step at a time and only as far as needed: the voice state of players who left, the chat history, players' effects, app state a server script assigned, and last other players' avatars and emotes (the joiner sees the default avatar until their next change). What cannot be dropped is counted as at most 1 KiB per player (measured worst case 695 bytes) plus the snapshot's fixed part: the joiner's own record, the URLs, the upload size, the AI names and the session and voice tokens. The fixed part is measured, not assumed: the server measures it at start-up for the largest joiner its configuration can have (8,811 bytes for `.env.example`, 9,378 with LiveKit, 18,903 with a 4,096-character `LIVEKIT_API_KEY`) and logs when it is over the 24 KiB expected, and each join measures its own. The snapshot carries the upload size as the number the server parsed (a `PUBLIC_MAX_UPLOAD_SIZE` padded with zeros used to be sent as written). The steps taken are logged once per combination.
  - **Joining.** A join is admitted when the real snapshot, after its steps, fits the cap; that is the only hard condition, and a snapshot that cannot fit is refused with the `player_limit` kick before any player is added (it used to close with 1011). The counted world state is an upper bound: a world stored over its budget (for example 5,100 apps: 1,035,412 bytes counted, a 592,143-byte snapshot) still takes a user with a stored rank, so an admin can come in to shrink or moderate it.
  - **Visitors.** A joiner without a stored rank of builder or above (the rank on the user's row; a free-build world rank, admin for everyone without `ADMIN_CODE`, and a session-only token grant do not count) must also leave room: with them here, the bound W + fixed part + P × 1 KiB ≤ 1,047,552 must still hold for 8 more players and 64 KiB more world state. Otherwise they get the `player_limit` kick (logged once per reason), before `WS_MAX_SOCKETS` or `playerLimit` would refuse them. A full 768 KiB world takes 174 visitors and an empty one 940 (159 and 925 with a 24 KiB fixed part); after them, 73 ranked users fit the bound at the full world, and 64 KiB of growth and 8 ranked users at the empty one. So 231 visitors can no longer keep an admin out, and 998 can no longer stop a 1 KiB addition. `connectionLimits` has no rank reservation of its own: `WS_MAX_SOCKETS` still counts every socket.
  - **Growth.** World growth is admitted against the players present (at least 64) with the measured fixed part, so 64 players always fit a world at its budget. To keep the counted parts bounded, the server refuses to start with `ASSETS_BASE_URL`, `PUBLIC_API_URL` or `LIVEKIT_WS_URL` longer than 1,024 characters or `AI_PROVIDER`, `AI_MODEL` or `AI_EFFORT` longer than 128, and a joiner's own stored avatar longer than 2,048 characters (only legacy data can be) falls back to the default.
  - **Existing worlds.** A world that is already over the budget loads whole, reports its totals and five largest items at start-up, and may shrink but not grow. When the counted total is over the snapshot cap too, the report says so as a count: visitors are refused, and a user with a stored rank joins while the real snapshot fits. Nothing stored is dropped or rewritten.
- server: a blueprint's `script` or `model` could name any file the server can read. Builder rank (which holding the token can give) was enough to set `script` to `/proc/self/environ` or `asset://../../x`. The server then read the file on every rebuild, and the AI `edit` and `fix` actions sent its text to the AI provider and saved the reply as an asset, so the server's secrets could leave through the AI. `model: '/dev/zero'` could exhaust the server's memory, and node agents read such paths on their own machine.
  - **Loading.** The server and the node agent read a local file only for `asset://<name>` (letters, digits, `.`, `_` and `-`, up to 128 characters), and only from directly inside the assets directory. No other value is ever read from disk. A path (`/…`), `blob:` and an invalid `asset://` name are refused with the reason and a short prefix of the value. With `ASSETS=s3`, and on the node agent, `asset://<name>` still loads from the assets URL. Remote loads are unchanged: an http(s) URL is fetched, and so is what the loader has always turned into one (`//host/x` and a bare `host/x` become `https://…`, which includes spellings such as `file:///x`); limiting where the server may fetch from is a separate change.
  - **Blueprints.** A new blueprint, or a change that sets `model`, `script` or `image.url`, must give `asset://<name>` or an http(s) URL with a lower-case `http://`/`https://` prefix. The client refuses anything else with a toast, the server with a revert. A stored blueprint that already holds another value still loads as it is, and changes to its other fields are accepted.
  - **AI.** `edit` and `fix` read only an `asset://<name>` script. For any other value nothing is read or sent to the provider, and the refusal is logged as the action's failure.
  - **Start-up.** Each stored blueprint whose `model` or `script` the server now refuses is logged once (`[network] blueprint "<id>" keeps a source the server no longer loads; …`) and kept unchanged. On the server that app shows the crash block until a builder replaces the value.
- scripts: the classes app scripts can reach are frozen. Before this, a script could replace a method on a shared class (`Vector3.prototype.add = …`), and the engine and every other app then ran the replacement, on the server and in every visitor's browser, until the process restarted.
  - **What is frozen.** `Vector3`, `Quaternion`, `Euler`, `Matrix4`, the interpolation classes and `Curve`, and the classes their instances lead to (THREE's own `Vector3`, `Matrix3`, `Keyframe`, and `Color`, which a material proxy returns): constructors, statics, prototypes and the methods themselves. Any write throws a `TypeError` in the script.
  - **Pointer callbacks.** `onPointerEnter/Leave/Down/Up` receive a new frozen `{ type, stopPropagation }` object for each call. The engine used to pass one shared, mutable event object to every app.
  - **XR poses.** Controller poses are copied into the pose objects as numbers. The browser's `DOMPointReadOnly` used to be passed to `copy()` of an object a script holds, whose `copy` the script can replace.
  - **`Object3D` is no longer given to scripts.** THREE's `Object3D` hands every listener the same event objects, through which a script could receive each object the engine later adds to its scene (and from a texture, the page's `document`). It was not documented; scripts use nodes for hierarchies.
  - **How.** Each prototype property is first turned into an accessor that still lets an instance take its own value (`src/core/extras/scriptClassPrep.js`), because THREE and the engine assign over prototype properties on instances (`_onChange`) and in constructors (`isVector3`). A plain freeze makes `new Object3D()` throw.
  - **Tests.** `test/scriptClassHardening.test.js` runs 24 attacks in real compartments under the real lockdown, checks that the engine and every node type still work, and walks everything reachable from a script's globals, instances and node proxies. The old test passed over an empty class list.
  - **Not covered.** A script can still obtain one of the math classes' internal temporary objects (for example through `Matrix4.decompose` with a made-up quaternion) and change that one object. That can disturb math for others; it gives the script nothing it could not already do to availability.
- server: the unused `Comput3Client` in `src/core/systems/ServerAI.js` is removed, together with the Comput3 API key written into it.
  - **Origin.** The class and key came from upstream Hyperfy (commit `57ee205`, 2025-08-20). The key was not issued for this project, so rotating it is up to whoever holds that Comput3 account.
  - **Not used.** The class was never constructed; the AI providers are still chosen by `AI_PROVIDER`, with `AI_API_KEY`.
  - **Still visible.** The key remains in this repository's history and in upstream.

### Still open
- nodes: `SkinnedMesh.unmount` does not clear `this.action`, so after a remount `play()` of the clip that was playing returns early and nothing animates.
- nodes: the SkinnedMesh `castShadow`/`receiveShadow` setters rebuild only when `this.handle` is set, which a SkinnedMesh never sets: a change after mounting is not applied.
- nodes: a video's unmount disposes its mesh geometry, which other nodes may share.
- nodes: a `uitext` under a `ui` throws on the server (`insertChild` of undefined: the server's `ui` has no layout node).
- nodes: in the Node test harness a box mesh made with `app.create('mesh', { type: 'box' })` inserted nothing (`Mesh.mount` returns early without `_geometry`); not yet checked in a browser.
- Phase 2: method shadowing with host (non-native) arguments remains for the objects a script makes and passes in (the THREE prototypes themselves are frozen, and the engine's own math objects a handle gives out are sealed, see Security), including interpolation, query/player getters and transitive matrix decomposition. Shared query vectors and live temporary output vectors remain script-reachable. The sentinel must be revisited when prototypes are hardened.
- Healthy physics shapes still do not resize on later scale edits (a skipped one mounts again once its transform changes).
- Persisted app repair and finite float32 checks at converted PhysX pose boundaries do not validate arbitrary script-composed transforms or every geometry. The player-transform hotfix already closed the octree expansion hang.
- Pending asynchronous native continuations after fatal shutdown remain a Phase 3b-1 residual; stopping ticks is not a global cancellation of native work. Generation-bound physics capabilities and a full teardown transaction are deferred. Emscripten abort state requires a restart; the dormant `prim-physics-test` example's direct PHYSX usage remains a follow-up. XR physical movement requires code review/headset verification.
- Model, avatar and emote limits: cost inside three.js and three-vrm that multiplies in ways the parser's charges do not capture is not proven absent; each review so far found another such place. Strings and extras are now small at the door, so what is copied, scanned or keyed once per object is at most 1024 characters a string and 64 KiB an object; what that still multiplies is bounded, not charged: three-vrm compares each VRM 0 material value's name, with " (Outline)" appended, against every material in the scene (at most 1024 characters a comparison, the walk counted); and each clone of a parsed scene after the parse (an avatar for each player) copies its userData, up to 8 MiB of JSON: about 180 MB held for the worst shape (lists of empty objects, 64 KiB an object), for each clone; an instanced export with small custom properties holds a few MB. The time limit refuses at the next charge after 10 s, but one long loop inside a library runs to its end, on the main thread. Up to 2^26 steps of work plus one per byte, and up to 10 s, may run on the main thread before a refusal (a file built to reach the work limit through one walk is refused after about 1.4 s on a desktop; a phone is slower). The server applies the same check and budget to models and emotes (it builds no avatars), with the morph-target charge at its largest since it has no renderer; its 10 s limit, like a client's, cannot interrupt a loop inside a library. The limits are per file and sized for VRoid avatars, 320 MiB of allocations beyond twice the file: with up to 12 files parsing at once inside the transfer slots (and files a user just picked taking none), a world of hostile files can hold several gigabytes at once before each is refused. Most of a VRoid avatar's cost is the morph textures three.js builds for each face geometry over all of the face's vertices; three-vrm's `VRMUtils.removeUnnecessaryVertices` would cut that, and the client does not call it. An avatar with far more blend shapes than VRoid's 56 (a "perfect sync" face of over 100, on as many primitives) may need more than the byte limit; none was measured. VRoid can export 4096 x 4096 textures, which have about twice their size to spare under the 36-megapixel limit per image (the samples' largest is 2048 x 2048). The time counts waiting too (an image decode, other parses interleaved), so a slow device loading many files at once could refuse a large honest one. Values inside the binary data are not read before parsing: index values beyond the vertex count, joint indices beyond the skin (a TypeError when the avatar is measured, so it fails to build), NaN or huge floats. three-vrm is bounded by counts computed before it runs; it is not metered while it runs. After parsing, turning a model into world nodes, cooking physics meshes and uploading to the GPU are bounded only by what was charged (sizes), not in time.
- Visitor-supplied avatar/emote assets can still contain invalid/extreme numeric data and corrupt that player's avatar, bones, nametag or bubble. Octree parking prevents those bounds from hanging the tree; it does not repair the asset. Asset numeric validation and an avatar fallback/cache lifecycle remain follow-ups. Voice positioning uses the validated player base transform rather than avatar bones.
- Shared positions beyond `1e6` per component are not broadcast; local movement is not constrained or corrected by this hotfix.
