  - **The form.** It shows the range in the amount field and a beta notice: start small, from a wallet holding only a little.
  - **Design.** goals/phase8-tip-beta-limits-design.md.

  - Article 8 limits liability concerning tips, except for intent or gross negligence, to the greater of the amount the tips causing the damage were meant to send and the amount actually sent (their total, if several).
  The English translation follows. The EVM wallet panel also tells users that tips are in beta and to connect a wallet holding only a small amount.
- server: the world page is now tried against a full Content-Security-Policy, as `Content-Security-Policy-Report-Only`. **This protects nothing**: a browser loads and runs everything exactly as before, and posts what the policy would have refused. It is here to learn what enforcing the policy would break for real visitors (a wallet extension that puts a script into the page, a wallet's in-app browser, a frame a wallet library opens) before anything is enforced; the four directives that were already enforced are unchanged.
  - **The policy.** `default-src 'self'`; scripts from the page's own origin, with the response's nonce (the page's two inline scripts carry it; a new one each response, and the page now says `Cache-Control: no-cache`), or from the script editor's folder on cdnjs, with `'unsafe-eval'` (app scripts are evaluated); styles from the page's origin, inline, or that folder; images, media and connections from anywhere; workers from the page's origin and `blob:`; frames from WalletConnect's two Verify hosts only. Enforced, it would stop an inline script or handler that got into the page and scripts of other hosts. It would not stop text that reaches an `eval` of the page's own code, injected CSS, data leaving through an image or a request, or whoever controls that cdnjs folder; and app scripts are not limited by it at all.
  - **The reports.** `POST /csp-report` (8 KiB a body; 20 posts a minute from one address, an IPv6 address counting with its /64, and 600 a minute in all, the rest answered 429). The server writes a line the first time an hour sees a kind of report, again at 10, 100, 1000 of it, and one line of totals for an hour that had any: `[csp] report-only: <directive> would refuse <origin, scheme or the browser's word>, asked by <path of a file of the page, or an origin or scheme>`. An hour holds 100 kinds; more are only counted. No query string, page address, referrer, script sample or extension id is kept. Anyone can post to this route: a line is what was posted, not proof of what a browser did, and someone can fill an hour's table with made-up kinds.
  - **Not covered.** The other static pages (`terms.html`) are not tried against this policy. Only the old `report-uri` form is sent (every engine posts it; the newer Reporting API is not used). The end-to-end runs (the world, uploads, the script editor with its workers, an injected wallet, the WalletConnect sheet, tips) report nothing in Chromium and WebKit; real wallet extensions, wallet in-app browsers, WalletConnect's relay and Verify frame against the real service, and voice were not tried and are what the reports are for.

  - **What they say.** The world is non-custodial and takes no part in transfers between players. Minors need a guardian's consent.
  - **Tips.**
    - **The address.** The opt-in is visible to the players in the world. The recipient's address goes to a sender when they start a tip, even one they never send, and it cannot be taken back.
    - **Sending.** Transfers go wallet to wallet on Polygon with no fee; the sender pays gas. There are per-token minimums and rate limits, and transfers cannot be undone.

Keys in the tips block stay out of the world's controls, so Tab reaches the link and Enter opens it without the chat; Escape still folds the panel.

- wallet: tips are confirmed on chain and announced (P2b) when the server has `EVM_RPC_URL_<chainId>` for the sign-in chain.
  - **Reporting.** Each tip intent now carries a server ticket. After the wallet returns the transaction hash, the client reports `{ ticket, txHash }` (new packets `evmTip` / `evmTipStatus`, appended; protocol version unchanged).
  - **Checking.** The server polls a shared, budgeted watcher. It matches only the token's `Transfer` log (sender, recipient, exact amount), not `receipt.from` or `receipt.to`, so EIP-7702 and sponsored transactions work. It waits for the `finalized` block, checks the block hash, and refuses transactions older than the ticket.

  - **RPC errors.** `RpcError` now separates JSON-RPC error answers from transport failures.

### Changed
- server: AI actions have a budget (`src/server/aiBudget.js`; see Security). A builder runs one action (create, edit or fix) at a time and 20 an hour; the world runs 2 at once and 60 an hour (`AI_MAX_PER_USER_PER_HOUR`, `AI_MAX_PER_HOUR`, `AI_MAX_CONCURRENT`). These numbers count admitted actions, not provider requests: a create is two requests (its script and its name, asked for together; its place is held until both have ended), an edit or a fix one, and the retries the OpenAI and Anthropic SDKs make on their own (two by default) are not counted.
  - **Deadline.** An action runs for at most 10 minutes in all (`AI_MAX_SECONDS`, from 1 to 86,400): reading the script, the provider requests with their retries, the name. Then its provider requests are aborted, its place is given back, and a reply that comes later changes nothing. (The SDKs' own timeouts end once a reply's headers have arrived; a reply that never finishes would have held its place for good.)
  - **Output limits.** Every provider client sets one: 16,000 tokens for a script, 4,096 for a name (Anthropic `max_tokens` and OpenAI `max_output_tokens`, both counting the model's thinking; xAI `max_completion_tokens`, which does not count its reasoning; Google `generationConfig.maxOutputTokens`, whose reference does not say). Before, only the Anthropic client set one. A reply cut off at the limit is an error, not a script.
  - **Refusals.** A request over a limit is not queued: the builder is told in chat. A value of an `AI_MAX_*` setting outside its range stops the server at start-up. The budget remembers at most 4,096 builders; when every one of them started an action within the hour or still runs one (which takes `AI_MAX_PER_HOUR` near that, or `AI_MAX_CONCURRENT` and `AI_MAX_SECONDS` raised so far that thousands of actions run for hours), a builder it does not know yet is told the AI is busy, and the others keep their counts.
  - **Placeholders.** `/create` places a "generating…" app before it asks. A create that is refused, fails, runs out of time or makes a script the world has no room for now removes that app, for everyone, also when its builder has left (the server does it; its blueprint stays, unused, as there is no way to remove one). `/create` without a description no longer places one.
  - A request is counted against the builder's user, or against the wallet of a builder who is one only by holding a token. The request itself is read into plain values: a prompt or an error text of at most 16,000 characters (longer is cut); of a crashed script's error, its `name`, `message`, `stack`, `fileName`, `code`, line and column and one level of `cause`, none of them required (a thrown `''` or `{ code }` can be fixed again; an error that says nothing is described to the provider by a fixed text).
- server: session tokens end. A new token lasts 180 days without being used, and every connect with a token older than a day gets a new one in the join snapshot (the client and the node agent store what the snapshot carries; the client now stores it before anything else in the snapshot is applied). A user who keeps coming back never notices. A user whose token ends unused joins as a new visitor: the name, avatar and rank stored with the old user are not theirs any more (wallets and tips are not tied to it). When that user had a rank the server logs it, so the operator can grant the rank again. Tokens made before this release have no end and stay valid until the secret is changed; they are renewed, with an end, the first time they are used.
- server: `JWT_SECRET_PREVIOUS` (optional) makes a planned change of `JWT_SECRET` possible without every visitor becoming a new user and every hand-granted rank being lost: tokens signed with the previous secret are still accepted, never issued, and are renewed under the new one. Start-up refuses the public template value for it and says while it is set. It must not be used after a leak of the old secret.
- server: `/status` gives the number of connected users in `connectedUsers`, not a list. See Security.
- scripts, players: which avatar and emote URLs a player can make everyone else load (see Security). **Upgrade note:** a client script that calls `player.setSessionAvatar('https://…')` or `player.applyEffect({ emote: 'https://…' })` for the local player worked for every visitor; now a URL outside the world is shown to the other players only when that visitor is a builder. Do it from server code (`world.isServer`), or use an `asset://` file. A server script's `setSessionAvatar` is now applied by the server itself and sent to everyone as a change to the player (clients saw a `playerSessionAvatar` packet to the owner, then the owner's own change); an effect's `emote` that is not an emote URL is left out of the effect that is sent. A client that sends its player's session avatar is now told the session avatar the server has afterwards, whether its value was taken or not (a value it already has changes nothing there), so when a client's change and a server script's cross, every client, that one included, ends on the one the server took last. The client numbers these updates (`sessionAvatarRequest`: a whole number the server hands back in its answer to that client alone, and keeps, relays and snapshots nowhere) and applies only the answer to its latest one, so a player who chooses again before the answer to an earlier choice arrives does not see the earlier avatar again on the way. An update the server never gets (the inbound gate dropped it) is not answered, and that client keeps showing its own latest choice, as before.
- server: a stored avatar that is a URL outside the world shows as the world's default avatar while its user is not a builder: from the join, and from the moment a builder stops being one (an admin lowers the rank, `/admin` again, a token grant ends, the world's rank setting is lowered). The stored value is kept, and shows again from a later join as a builder. A builder who stops being one also loses a session avatar or emote outside the world that no server script chose; everyone, the player too, is told with the packet of any other change to the player. A stored value is read as the loaders read it, resolved: `//host/a.vrm`, `host/a.vrm` or an `https://` URL with white space around it is a URL outside the world too, and the same spellings of a file of the world's own store (`//world.example/assets/a.vrm` or `world.example/assets/a.vrm` with the assets at `https://world.example/assets`) are the user's own, with a query or a fragment or not. A page path (`/assets/a.vrm`) counts as outside: the browser resolves it against the page, and the server cannot know that the page is served where the assets are. The `avatar` parameter of a connection (the node agent's `AGENT_AVATAR`) is taken as a URL outside the world only for a builder.
- client: the Custom Avatars setting says what it does: visitors may upload their own VRM, to this world.
- docker: the image's health check asks `/health`, not `/status`.
- server: `/admin <code>` answers a wrong code ("Wrong admin code.", to that player only) and slows guessing down (`src/server/adminCode.js`; see Security). After three wrong codes a user id and an address (an IPv4 address or an IPv6 /64) wait 10, 20, 40 and then 60 seconds between attempts; an address's /56 and /48 wait 10 seconds after 32. During a wait no code is looked at, the right one included, and each connection is told once per wait. Waits are measured on a monotonic clock, so a change of the system time does not move them. The table of recent failures holds 8,192 keys; when room is short, user ids give way before addresses, and an attempt from an address that finds no room is not looked at either (it is answered as a wait, and that connection waits 10 seconds). A connection is closed at its 21st attempt (kick code `admin_attempts`). The client and the server decide what is the admin command in one place (`src/core/extras/chatCommand.js`): a first word that is `admin` in any letter case once trimmed, so `/Admin`, `/ admin` and the like are the admin command on both sides, and none of them reaches scripts as a `command` event, on the client or on the server.
- moderation: the kicked player's overlay says "You were removed by a moderator." (and "Try again in a few minutes." when they come back too early); `agent.mjs` stops on the `kicked` code as it does on `moderation`. Kicks are logged with both user ids.
- server: a world's admin mode is decided once from the environment: a non-empty `ADMIN_CODE`; open to all (no code outside production, or `ADMIN_OPEN=true`); or, **in production with no code and no `ADMIN_OPEN=true`, locked**: nobody is an admin by default and `/admin` does nothing, where every visitor used to be an admin. Stored ranks apply in every mode. The server starts in all three and says at start-up which it is (never the code or its length). It also warns about a code under 16 characters (the brake still allows thousands of guesses a day from each network, so only a long random code holds), and about one the chat cannot carry: one with a space in it or whitespace at either end, or one longer than the 493 characters a chat line leaves after `/admin `. `/status.protected` is false only for an open world (it was true for an empty `ADMIN_CODE`).
- server: start-up logs where client addresses are read from (the configured header or the connection). The per-address limits for connections, uploads and wrong admin codes all use it; behind a proxy that is not named in `UPLOAD_CLIENT_IP_HEADER` every client has the proxy's address.
- scripts: the numbers and texts of a node that become a size are kept inside a range (`src/core/extras/boundedValue.js`). A value outside its range becomes the nearest bound, `NaN` becomes the property's default, a text over its limit is cut; nothing new throws, and reading the property back gives what was kept. These are not a defence against a builder who wants to stall visitors (a script can loop); they keep a wrong value (a bug, a `NaN`, `1e9`, a pasted book) from costing every visitor the tab.
  - **UI.** `width` and `height` 0 to 16,384, `res` 0 to 16, `size` 0.000001 to 1,000,000. The canvas has at most 4,096 pixels on a side and 8,388,608 in all; a larger UI keeps its size, layout and pointer coordinates and is drawn at a lower resolution. (A canvas over the browser's own limit cannot be drawn on, and each pixel costs memory twice: in the canvas and in its texture.)
  - **Text.** `uitext.value` 10,000 characters and `fontSize` 0 to 1,024; a nametag's and an action's `label` 256 characters.
  - **Particles.** `max` a whole number up to 20,000, `rate` up to 100,000, at most 64 `bursts` with a `count` up to 20,000, `duration` at least 0.01 s, `timescale` 0 to 100; spritesheet rows and columns 1 to 256 and its frame rate 0 to 1,000 (one that is not a number, or is 0 or less, shows the first frame); a start value (`life`, `speed`, `size`, `rotate`, `color`, `alpha`, `emissive`) 256 characters and an over-life curve 4,096 (64 points of the longest numbers JavaScript prints fit), of which the worker reads up to 64 points and two values a point. In the worker, one step starts at most as many particles as the pool holds over its rate, distance and bursts together, and looks for a free particle from where it found the last one: a step costs the pool's length once (it was the pool's length per particle started, and a rate without end with particles of no life never returned).
  - **Audio, video.** `volume` 0 to 100, and the spatial numbers inside what Web Audio accepts (`refDistance` and `rolloffFactor` not negative, `maxDistance` above zero, cone angles 0 to 360, `coneOuterGain` 0 to 1): a value outside threw in the middle of `play()`, or in the setter of a node that was playing. An audio node's `currentTime` and a video's `time` (`currentTime`) are finite and not negative (`NaN` is 0). `audio.setPlaybackRate(rate)` reads the rate by the engine's number rule and keeps it between -1,000 and 1,000 (`NaN` is 1): a rate that is not finite as a float (`NaN`, `Infinity`, `1e100`) threw from the ramp of a playing sound; on a sound that is not playing, and on the server, it does nothing (the server threw).
  - **Sky, image, video.** The sky's `rotationY`, `sunIntensity`, `fogNear` and `fogFar` are finite (`NaN` counts as not set; one `NaN` there blacked out the scene). An image's or video's `width` and `height` are finite and not negative (`NaN` counts as not set), a video's `aspect` 0.001 to 1,000.
- scripts: `node.cursor` takes CSS cursor keywords only (`pointer`, `grab`, `crosshair`, ...); see Security. Of an image cursor with its fallback (`url(hand.png), pointer`) the closing keyword is used and read back; a value without a keyword reads back as `null` and the default cursor shows. One warning is logged; nothing throws.
- models: a collider in a model file gets a layer a script could set. A `layer` custom property that is not `environment`, `prop` or `tool` (the engine's own `player` layer included, which a script's handle already refused) gets the default (`environment`); the model still loads. This is one rule for both ways in, not a new protection: the layer carries no authority.
- client: a player whose avatar cannot be loaded (a missing file, one the loader's limits refuse, a file that is not a usable avatar) appears with the built-in avatar. Such a player was a name over nothing, for everyone, for as long as they stayed. A player who already has an avatar showing keeps it when a new one fails, also when the new one cannot be made, placed or mounted, or fails once it is placed (its heights cannot be read, the name or the bubble cannot be moved): the new avatar is mounted and set up before the old one goes, and one that fails on the way is taken out again, leaving the player as it was; its failed mount is reported with the load, not as an unhandled rejection. A load turned away only because the loader was busy is asked for once more after 15 seconds, whichever avatar shows meanwhile; a later choice (even of the same avatar) has its own load, and the earlier retry does nothing.
- client: `window.world`, `window.THREE`, `window.app`, `window.prims` and `window.preview` are set only on a page served from localhost, or when `PUBLIC_DEBUG=true` (`.env.example`). This is not a protection: code that runs in the page can reach the world without these names. It keeps a stable name for console snippets off a deployed site. Debug `console.log` calls that printed AI prompts, a script's `world.open()` target, undo and avatar preview details are removed.
- scripts (behavior changes from the script → host boundary work, see Security):
  - `world.chat(msg)`: only `body` and `from` are read; `fromId`, `id`, `kind` and any other field are ignored. The message is an app line (`kind: 'app'`, the app's name in `app`), never a player's line, so it no longer pops a player's bubble and the `chat` event it fires has no `fromId`. A client script's broadcast goes to the server as a new `appChat` packet and the server relays it as that app's line (it used to arrive as the visitor's own chat).
  - `app.fetch()` rejects with a built-in error (as the standard `fetch` does) when the request fails; it used to log and resolve `undefined`. A request still open when its app is rebuilt, crashes or is removed is aborted and never settles, without a log line.
  - `props` (and `app.props`/`app.config`) is the instance's own copy: changes stay in that instance until its next build, and `configure`'s `initial` values no longer reach the shared blueprint or the join snapshot. A blueprint without props gives the script `{}` (it was `null`). Exported `.hyp` files still carry each field's `initial` for keys the app does not set, as before; duplicating an app copies only the props the builder set (the copy's script applies its own initial values).
  - `app.configure()`: a field whose `key` is not a string of 1-64 characters, or is `__proto__`/`constructor`/`prototype`, is dropped with one console warning per app (a `section` or `button` may still have no key); properties the sidebar does not use are dropped; at most 256 fields. `when` rules see a field's `initial` value when the prop is unset.
  - `control.setActions()`: at most 64 actions, labels cut to 128 characters; the objects passed in are not changed (no `id` is added).
  - Nodes: adding a node to itself or to its own descendant throws; more than 20,000 live nodes or 256 levels in one app crashes it. A boxed `String` is no longer accepted as a nametag label (throws as other non-strings) or an action label (shows the default).
  - `setTimeout` throws past 1,024 pending timers; calls from a removed app's script (after its `destroy` event) throw.
  - `world.raycast()` and the player/bone/world-matrix getters listed under Security return a new object each call.
  - The engine's math objects a handle gives out by reference (a node's `position`, `quaternion`, `rotation`, `scale` and `matrixWorld`; a joint's offsets, rotations and `axis`; a UI's `offset`; a control's camera, poses and sticks; a skinned-mesh bone's transform) are sealed: their values change as before, but adding, redefining or deleting a property throws a `TypeError`, a matrix's `elements` cannot be replaced, a component keeps a number (a string, a boolean or `null` given to one is converted, as `node.position.x = '2'` and `.fromArray(text.split(','))` expect; `undefined`, a Symbol, a BigInt and any object, a boxed `new Number(2)` included, are `NaN`, an object's `valueOf` never called; an Euler order that is not a string leaves the order), and `_onChangeCallback` cannot be replaced (a script could replace it, and the engine then ran the script's function on every change, inside a physics step or a commit). A node's own `position`, `quaternion`, `rotation` and `scale` are the engine's objects; a value written straight into one of their fields (`_x`) is read by the engine by the same rule (an Euler `_order` that is not a string as `'YXZ'`). The rest (`matrixWorld` and its `elements`, joint, UI, control, bone and particles vectors) are views of the engine's objects that behave like them and keep numbers in their fields by the same rule. A control's entries (`camera`, buttons, poses, sticks, `scrollDelta`, `pointer`, `screen`) are sealed: their fields can be written as before (`camera.write`, `camera.zoom`, a button's `capture` and `onPress`), but a field cannot become an accessor, nothing can be added or deleted, and the engine's parts (the camera's and a pose's vectors, a stick's `value`, the pointer's and screen's getters) cannot be replaced. A rigidbody's `getPosition()`, `getQuaternion()` and velocity getters called without a target return a new object each time (they returned one kept per body). A particles node's `force`, `velocityLinear` and `velocityOrbital` are engine copies of the vectors set (reading one back gives the copy, not the script's object).
  - A call whose own arguments end its app's run (a getter, `toString` or `valueOf` that removes or rebuilds the app) makes nothing and throws `[app] this app has stopped`. Names and types are converted once, before anything is made: an event name (`app.on`, `world.on`), a node type (`app.create`), a `world.load()` url, a skinned mesh's clip name (and its `fade` and `speed`, as numbers). `setVoiceLevel()` takes a string only; any other value is reported and changes nothing (it used to reach the voice system, which refused it). `world.getPlayers()` throws the stopped error from the player stage on also when nobody is in the world.
  - Node setters keep plain values: one that takes a number, a string or a boolean throws for a boxed primitive (`new Number(1)`) or a Proxy that poses as one (lodash's checks accepted both); `node.active`, a joint's limits and `collide`, and `lod.insert(node, maxDistance)` throw for an object. A UI's `padding`, `margin` and `scaler` and a particles node's `shape`, `bursts` and `spritesheet` read back as the node's frozen copy (changing it throws a `TypeError`), and an entry of a particles `shape` or `spritesheet` or of a UI `scaler` must be a primitive (a `scaler` used to be kept as the script's own array, read every frame). An `applyEffect` field that is an object or a function (`emote`, `snare`, `turn`, `duration`, ...) refuses the effect, as an invalid value does. `app.off` and `world.off` convert the event name as `on` does.
  - A node handle's setters act on the handle they are called on or on an object that inherits from it (`Object.create(node)`); a setter copied to another object or called without a receiver throws `[node] not a node`, and one called on the handle of a node without that property throws `[node] a group node has no castShadow to set` (it threw a raw `TypeError` from `Function.prototype.apply`). Methods keep their `name` and `length`. A handle follows its node: when another app's live run places the node, every handle of it (also one the first app kept) works for that run.
  - Handles belong to the app run that got them: after a rebuild, crash rebuild or removal, the old run's `world`, `app` and player objects throw `[app] this app has stopped`, its control answers but changes nothing (`setActions`, `hideReticle`), its `fetch` and body reads never settle, and its nodes cannot be mounted again with `active = true`. Every acting player method (`damage`, `heal`, `applyEffect`, `cancelEffect`, `setSessionAvatar`, `teleport`, `push`, `screenshare`, `setVoiceLevel`) now also refuses a crashed app, as other calls do (an effect handle's `cancel` refuses once the run has ended); the app's own `destroy` handler works as before. Player objects no longer have `$cleanup`.
  - A released control's action hints leave the HUD and it can no longer hide the reticle.
  - `world.overlapSphere()` returns new plain `{ tag, playerId }` records; raycast and overlap report a `tag` only when it is a string, and a rigidbody `tag` must be one (a boxed `String` throws). `world.get()` returns a copy of the stored value.
  - `control.pointer.coords/position/delta` are new vectors on each read; an app's `onTouch`/`onTouchEnd` receive a copy of the touch; a camera with `write` moves only to finite values.
  - The engine's `enter`, `leave`, `health` and `command` world events are frozen copies.
  - Particles `shape` and `bursts`, UI `margin`/`padding` and Sky `sunDirection` are the node's own copies (reads of `sunDirection` return copies); a non-finite `sunDirection` throws.
  - Action `distance`/`duration` and Nametag `health` must be finite primitive numbers (a boxed `Number`, `NaN` or `Infinity` throws); a node `cursor` must be a string of at most 128 characters or `null`.
  - Moving a mounted node (also one in world space) under another node remounts it there; a node never placed in the world is not mounted by `active = true`; `world.add` of a node mounted for another app moves it.
  - `setTimeout` with a delay that is not a number or a numeric string uses `0` (its `valueOf` is not called).
  - A client script's `world.chat(msg, true)` reaches the others as an app line through the new `appChat` packet (see Security).
  - Persisted settings and the join snapshot go through the settings rules; an invalid stored value is replaced by that key's fallback (logged once).
  - `material.color` (mesh materials) returns a new `Color` with the material's values; changing it changes nothing (assign a CSS colour string, as documented). Material `textureX`/`textureY`/`emissiveIntensity` take finite primitive numbers and `fog` a boolean; a video's `material.textureX`/`textureY` take finite numbers.
  - `world.getPlayer()` handles are per app run and are no longer replaced when a script changes `destroyed` on one; a player looked up from a cleanup callback (an effect's `onEnd`) while the app is being torn down throws `[app] this app has stopped`.
  - `fetch` and `setTimeout` are bound to the run that received them: kept and called after a rebuild, `setTimeout` throws `[app] this app has stopped` and `fetch` starts nothing and never settles.
  - A world-space node another app takes over (its `world.add`, or moving it under its own node) leaves the first app's world-space list: the first app's `world.remove` and teardown no longer touch it.
  - An app's `onTouch`/`onTouchEnd` receive one frozen touch object per touch (the same at start and end) whose `position`, `prevPosition` and `delta` follow the touch as new vectors on each read. `control.pointer.lock()`/`unlock()` do nothing once the control is released. XR ray poses no longer carry the engine's smoothing state (`lPosition`/`lQuaternion`).
  - Action nodes' default `onStart`/`onTrigger`/`onCancel` are frozen functions; the engine calls script callbacks with `Reflect.apply`, so a `call`/`apply` property on a callback is not used.
  - `mesh.material` and `video.material` are frozen objects bound to the run of the app the node is mounted for: the same object within the run (also for meshes of the run that share a linked material), another object for another app. Setting a property on one kept after that app stopped throws `[app] this app has stopped`; reading still works, and the app's own `destroy` handler can still set it.
  - Another app's root (what its `app` stands for) cannot be moved: `world.add`, `world.attach` and `node.add` throw `[…] cannot add another app's root node`. An app moving its own root works as before, except under a node that is not placed anywhere yet.
  - While an app is torn down, an effect's `onEnd` (or any other cleanup callback) can end things through the app's player handles (`cancelEffect`, `setVoiceLevel(null)`) but `applyEffect` and `setVoiceLevel(level)` throw `[app] this app has stopped`.
  - A pointer lock taken through a control ends when that control is released (or its app stops or is rebuilt); a lock another control took is left alone, calling `app.control()` again hands the lock to the new control, and the control's own `onRelease` can still call `pointer.unlock()`. A touch object kept after its touch ended or its control was released answers with the touch's last values.
  - `app.control()` throws `[app] this app has stopped` once the app's teardown has started (in a `destroy` handler, an `onRelease` or an effect's `onEnd` run by the teardown); a control of an app run that has ended does nothing. During `onRelease`, `pointer.unlock()` works only for a lock the control still holds. `video.material` is `undefined` until the video is mounted (and once it is unmounted), as `mesh.material` is. Pointer callbacks (`onPointerEnter`/`Leave`/`Down`/`Up`) of an app run that has ended are not called. While an app is removed, its own cleanup callbacks can still end its effect and voice level (`cancelEffect`, `setVoiceLevel(null)`).
  - App teardown (see App.md, Teardown) distinguishes what a run owns from effects on shared state. What it owns (nodes and what they hold, controls, player effects and voice levels, listeners, timers, requests, object URLs) is released at teardown and cannot be made again by the run once its stage has begun: `world.getPlayer()`/`getPlayers()` and starting effects or voice levels from the player stage on; `world.add`/`world.attach` and every method and setter of a node of the run from the node stage on, and for good once the run has ended (`[app] this app has stopped`; getters keep reading); listeners, `fetch`, object URLs and `setTimeout` from their own stages. Effects on shared or persistent state (chat, sends, storage, teleport/push/damage/heal, session avatar, screenshare, wallet queries, `world.open`) are allowed while the run is alive, including in the callbacks a removal's teardown runs (they used to be refused after the `destroy` event), and refused once it has ended. A node added under a node that is unmounting is not mounted; an unmounted sound, skinned mesh or UI image does not play, animate or load. `world.getPlayer(id)` returns `null` for a player that is leaving and `world.getPlayers()` leaves it out; a handle whose player has left starts no effect or voice level (`[player] this player has left`). `URL.createObjectURL` URLs belong to the run whose `fetch` made the blob (at most 256 live, all revoked when the run ends); `URL.revokeObjectURL` is new and revokes only those.
- client: a model, avatar or emote may only use what is inside its file. A `.gltf` or `.glb` that names an external buffer (a `.bin` by URL or relative path) fails its load; one that names an external image loads without that texture. Embedded buffers and images, and `data:` URIs, load as before. Until now a file's absolute dependency URLs (`https://…`) were fetched, for an uploaded `.glb` or `.vrm` as for a remote file, outside the loader's size limits and deadlines; only relative ones never resolved (files are parsed without a base path). A file that relied on absolute URLs now fails (buffers) or loads without those textures (images). The server cannot load external files either.
- client: an image a model, avatar or emote decodes must be a PNG, JPEG or WebP, by its bytes whatever `mimeType` it declares; a file with any other image it decodes (GIF, BMP) fails its load with a reason. An image used only through `KHR_texture_basisu` is never decoded (this client has no KTX2 decoder and uses the fallback image). AVIF textures inside models are not decoded either, in any browser: the parser takes `EXT_texture_avif` as unsupported and uses the fallback image (an AVIF image cannot be sized before its decode; a file that requires the extension fails its load with a reason). Stand-alone AVIF images still go to the browser as before. An image named by URL is not fetched, as before. The bundled models and avatar decode PNG and WebP only. Stand-alone images keep every format the browser decodes.
- client: an asset in the world's own store is loaded and kept once whatever its query or hash: `asset://x.glb?s=2` and `asset://x.glb` are one download and one result, and `loader.get`/`has` answer for either. Playback options in an emote's query (`?s=`, `?l=`, `?g=`) still apply, since the avatar reads them from the URL it was given. A URL from another host keeps its query, which can name a different resource.
- server: remote models, emotes and scripts named by a blueprint are fetched through one outbound request policy (`src/core/extras/outboundFetch.js`). App scripts' `fetch` goes through it too, on the server and the node agent (in a browser it is the browser's fetch, as before): see **Scripts** below. Avatars are stubs on the server and are not fetched.
  - **Where it may connect.** `http` and `https` only, no credentials in the URL, and only public addresses. IPv4: loopback, private, link-local (cloud metadata), carrier-NAT and the other special ranges are refused. IPv6: an address is refused when it is not global unicast (`2000::/3`), so loopback, link-local, unique-local, multicast, NAT64 and the IPv4-compatible and IPv4-translated forms are refused, or when it is in a special-purpose range inside it (the `2001::/23` protocol assignments such as Teredo and ORCHID, documentation, 6to4) or in the returned 6bone space `3ffe::/16`. An IPv4-mapped address follows the IPv4 rules. No allocation table is kept: an unallocated block inside `2000::/3` is admitted (it has no route on the public internet), so new address space works once it is allocated. The host is resolved once through DNS (A and AAAA; the hosts file is not consulted), every address must be public, and the connection is made to a checked address, so a second DNS answer cannot change the destination. The first IPv4 answer is used, or the first IPv6 one; if connecting to it fails (refused or unreachable) or has not connected within a third of the time left, but at least 250 ms, one more checked answer is tried, of the other family when there is one. That attempt is still within the one deadline: a deadline shorter than the first attempt's 250 ms ends the request before it. The connected address is checked again before anything is sent, and TLS is verified for the URL's name. Redirects (at most 3) pass the same checks, and the body of a redirect that is followed is not read.
  - **Limits.** One deadline covers the whole request: resolving, connecting, redirects and the body. A remote load may take 30 s and 32 MiB of decoded body. At most 16 requests run at once and more are refused rather than queued; a request keeps its slot until its DNS queries have ended. The slots cover the exchanges only, not what a caller does with a response afterwards (the loader's parsing has its own bound, below). Responses being received share a 64 MiB budget, which covers a request until its response is handed over (the body is held once, as received); what the caller then reads or keeps is the caller's memory. The handed-over body still follows the caller's `signal`, as fetch's does: an abort before it is read to the end (an empty body included) makes reading it reject with the signal's reason, an `AbortError` for a plain `abort()`. A response without a body (HEAD, 204, 205, 304) has nothing to abort: reading it after an abort gives `''`, as native fetch does on Node 24 (on Node 22 native fetch rejects). Bodies are decoded from gzip and deflate only, and a response without a body (HEAD, 204, 205, 304) is not decoded.
  - **Requests.** The options are fetch's: `method` (GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS), `headers` (repeated names are combined as fetch combines them, Cookie with `; `; every header sent, the ones the policy adds included (Host, Accept-Encoding, `Connection: close`, Content-Length, which is also `0` for a POST, PUT or PATCH without a body, and an inferred Content-Type), is set explicitly, so Node adds none, and is validated and counted before anything is resolved or sent: at most 64 and 16 KiB of names and values in all, so a GET, HEAD, DELETE or OPTIONS without a body leaves 61 to the caller and a POST of a string 59; a Blob's type must be a string), `body` (a string, an ArrayBuffer, a typed array or DataView, or a Blob, at most 1 MiB, with the Content-Type fetch infers), `signal` and `redirect` (`follow`, `manual` returns the redirect, `error` rejects; an empty `Location` is the same URL again). A request that a redirect turns into a GET loses its body and fetch's request-body headers (Content-Encoding, Content-Language, Content-Location, Content-Type). `mode`, `credentials` and `cache` mean nothing on the server and are ignored; any other option, and a GET or HEAD with a body, is refused.
  - **Trusted origins.** The world's own assets URL is exempt from the address check (it is local in development and may be a private object store). `OUTBOUND_TRUSTED_ORIGINS` lists further origins, comma separated. Upgrade note: a world whose blueprints load from a host on a private network must list that origin.
  - **Scripts.** A script's `fetch()` on the server used the global fetch, so a script could request the server's own loopback, its private network and cloud metadata addresses, with responses of any size. It is now made by the same policy (an instance of its own, so scripts' requests and the server's remote loads cannot take each other's slots or memory), with the app as the caller: public addresses only (and the trusted origins), a response of at most 8 MiB of decoded body, a request body of at most 1 MiB, 15 s for the whole request, at most 3 redirects, and at most 4 requests in flight per app (16 for all apps together); a request beyond those is refused, not queued, and its promise rejects with a `TypeError` whose message says why (`outbound request refused: …`, `outbound request failed: …`). The response resolves once its whole body has arrived (it used to resolve at the headers), so an endpoint that keeps its response open fails at the 15 s. The headers the policy sets or drops (Host, Connection, Content-Length, Accept-Encoding, Transfer-Encoding, Proxy-Authorization and the other hop-by-hop ones) are no longer the script's to send, and a decompressed response has no `content-encoding` or `content-length` header. A request body is sized and sent by its own bytes: an `ArrayBuffer` or view is copied by the host without running the constructor it names (`Symbol.species`) or reading `byteLength`, `byteOffset` or `buffer` properties a script put on it (a subclass with an own `byteLength` of 1 used to pass the request-size check with a megabyte of bytes). A `data:` URL and an object URL made for a script are still read locally, by the platform's fetch (no other `blob:` URL of the process is); the limits above are those of `http`/`https` requests and do not apply to these reads, which hand over bytes the script already holds. They are read to the end without the run's abort signal: on Node 24, aborting the signal of such a response while its body was unread (an app removed or rebuilt after `fetch('data:…')`) threw from the platform's abort listener and ended the server process; Node 22, which the Docker image pins, is not affected. Upgrade notes: a server-side script that calls a service on a private address needs that origin in `OUTBOUND_TRUSTED_ORIGINS`; one that starts more than 4 requests at once must wait for some to finish; a response compressed with anything but gzip or deflate is refused (the request asks for those only). See docs/scripting/Utils.md, Fetch.
  - **Models.** On the server a model or emote may only use what is inside its file (`data:` and `blob:` URIs): nothing outside the file is ever requested. An external buffer fails the load; an external image is not fetched, and the model loads without it (the server draws nothing).
  - **Cache.** The server loader keeps at most 512 finished loads of every kind and location (the world's store and remote URLs alike), the least recently used leaving first. A load in progress is never dropped, so while more than 512 are in progress the cache holds them all. What loads in progress hold is bounded per kind: models and emotes, local and remote alike, are read and parsed in 4 turns (a turn covers the read and the parse, and the others wait in order without having read anything). A deadline frees a turn whose read (30 s) or parse (60 s) does not settle: that load fails and the turn goes to the next. A read given up is cancelled (its outbound request is aborted, a local read stops); a parse cannot be, so a parse whose turn expired may still be running, and holding its memory, until it settles, outside the 4 turns. A deadline cannot interrupt a parse that blocks the event loop, and a phase that completes before its timer has run is accepted however long it took, so a large but valid model still loads on a slow host. A destroyed loader fails the loads waiting and those in a turn, and starts nothing for them, a remote script takes one of the 16 outbound slots while it downloads, and a local script read has no bound of its own. A load that finishes after it was replaced or after the loader was destroyed writes nothing. One resource has one entry whatever its spelling (surrounding spaces, a fragment, a default port); an `asset://` name and the assets URL it maps to share one where assets are read over HTTP, while with a local assets directory the file and the URL are separate resources and keep separate entries. A query names another resource. Failed loads are not kept, so a URL that starts working is loaded on the next request. Every avatar shares one entry.
- scripts: `world.set` has limits, and `world.get` returns a copy. A key is a string of 1 to 128 characters, a value at most 64 KiB as JSON, at most 1,024 keys and 4 MiB in total (`STORAGE_MAX_KEYS`, `STORAGE_MAX_VALUE_BYTES`, `STORAGE_MAX_BYTES`). A `set` past a limit throws and leaves the store as it was; it used to grow without bound, and each write rewrote the whole file. A store that is already larger loads as it is and may shrink; a key stored before the key rule (longer than 128 characters, or empty) can still be overwritten without growing and deleted. `world.set(key, undefined)` deletes a key (it used to log an error and change nothing), and a value that cannot be turned into JSON throws (it used to be logged and dropped). `world.get` used to return the stored object itself, so one app could change what another read without calling `set`. Both are now documented in `docs/scripting/world/World.md`.
- scripts: `world.set` throws ("the server is stopping") once the final save on shutdown has started, so the server never acknowledges a value it will not write. When the stop begins, app timers are cleared and no app starts its script again: a build still waiting for its assets, a crash rebuild or a blueprint change does nothing from then on.
- server: an upload is refused (`507`) when free space cannot be read, instead of being let through.
- ci: the end-to-end job also runs on every push to `main` and weekly (Mondays 04:23 UTC), so `main` is checked even when a pull request skipped the suites through its paths filter.
- chat: a user's message always shows a name (`Anonymous` when empty), and names made only of spaces or invisible characters are refused on the server and the client, so a user message can no longer look like a system message.
- wallet: a Solana verification that times out after the verify request was sent is withdrawn on the server (`revokeBuilderByToken`), so a late success cannot leave the server verified (and a builder) behind an unverified panel.
- network: tip packets are appended (`setEvmTipReceive`, `requestEvmTipIntent`, `evmTipIntent`, ids 35-37) with inbound caps of 32 and 192 bytes.
- network: EVM wallet packets are appended to the packet table (`requestEvmNonce`, `evmNonce`, `requestEvmVerify`, `evmWalletStatus`, `revokeEvmWallet`, ids 30-34) with inbound caps of 128, 512 and 16 bytes for the client-sent ones. Existing ids and the protocol version (`v=2`) are unchanged, so existing node agents keep working.
- stage, prims: memory for prims and linked meshes stays bounded (Phase 3b-2b-2). A Model with no instances is released after 10 s of world time (its instanced mesh, geometry clone and BVH); the material it rendered with is kept per Model id, so scripts' material proxies and their edits survive visible toggles, LOD switches and rebuilds, and the uber-shader hook is installed once per material. An unlinked mesh disposes the material and textures it cloned. Prim geometry keys are finite and the same in every process: tapered cylinder radii snap to a 1/64 grid and torus tube ratios to a log2 grid of 1/8 octave (computed from the float bits, since Math.log2/Math.pow may differ by engine), and a ratio outside 2^-10..2^10 is invalid (no visual, no physics). Prim materials round metalness and roughness to 0.05, so untextured materials form a fixed palette (at most 21 × 21 × 21 × 2) that every process builds the same way; textures are first come, with at most 256 texture strings and 1024 textured materials per process, beyond which a prim renders untextured with one warning. Kept linked materials are capped at 8192 or the live Models, whichever is larger (oldest released first), and Stage.destroy disposes Models and materials. Mesh box and sphere geometries are shared by size and held while a mesh is mounted with them; at most 1024 unused ones per shape stay cached (least recently released first out, disposed when evicted), so the cache holds the sizes that mounted meshes use plus 1024 per shape (how many meshes an app mounts is not limited here). A geometry's id is its shape and size, so a linked mesh that was inactive while its geometry was evicted comes back to its Model and material edits, as long as the stage still keeps them (the Model for 10 s without instances, the material within the kept-material limit). An exception while a mesh is inserted into the stage takes the mesh or its instance back out instead of leaving it rendering (a non-finite matrix is parked by the octree, not refused, and still renders as before). Linked render flags count only when they are `true`. Values that reach a cache key must be primitives (a `Number`, `Boolean` or `String` object, whose own `toString` could mint keys, is refused): Mesh `width`, `height`, `depth` and `radius` (which also refuse `NaN` and ±Infinity now), Prim `metalness`, `roughness` and `opacity`, Prim `texture`, and Prim `doubleside`, `castShadow` and `receiveShadow`. A Prim keeps a plain copy of the size it is given (at most 16 values) and hands scripts a copy back, so a custom iterator, index getter or later edit cannot change the size after it was checked.
- physics: a Collider skipped for its scale, extent or pose, a Prim skipped for its size, scale, extent, position or mirror, and a RigidBody skipped for its position mount again once that transform changes (an extent skip keeps its cooked mesh, so the retry does not cook again; moves that leave the checked transform unchanged do not retry).
- physics: no native allocation outlives its node, and unchanged values do not rebuild (Phase 3b-2b-1). Per mount, RigidBody leaked one or two PhysX objects, Controller four, and every RigidBody and Joint node kept scratch objects forever; a visible Controller leaked its capsule geometry, BVH and material on clients. Assigning the same mass, damping, centre of mass, Collider size/material/flags, Controller size or Joint limit every frame rebuilt the node every frame, and a RigidBody rebuild silently dropped its joints for good. Joints now detach before their body's actor is released and mount again on the new one, wait (instead of pinning the other body to the world) while a body has no actor, and a joint's failure stays in its own app. A native throw mid-mount no longer leaks temporaries or publishes a stale physics handle. Meshes: the vertex count and every index are checked before anything is allocated (whole triangles, indices inside the vertices); each mesh may have 200 000 vertices and 200 000 triangles (convex hulls 50 000 points), each app 400 000 and the process 2 000 000 vertices plus triangles of live cooked meshes (the production world's largest mesh has about 10 000 triangles), so one app cannot exhaust the wasm heap, which only grows and aborts at 2 GB.

Storage writes no longer overlap.

- server: the clean-up (`CLEAN`) has a stated contract, keeps what the world names by its file name whatever URL it is written in, deletes nothing when it cannot read what it must, and, with `ASSETS=local`, moves what it removes to a trash instead of unlinking it.
  - **The contract.** It keeps every store file whose name appears as a literal in the persisted world data or in the source of a store script reachable from that data, and deletes nothing when it cannot read something it must read. The code it follows is exactly: the store file a blueprint's script names, whatever its extension, and any `.js` store file named as a literal in that data or in code it follows. It cannot see, so such a file is removed: a name computed at run time (`'abc' + 'def.glb'`, a template, a hash) or written with JavaScript escapes (`'\x61bc.glb'`); code built at run time, that is code a script fetches or assembles and evaluates itself (`fetch` and `Function`), wherever it is hosted, the store included, and whatever that code names (no engine API runs another script: `world.load` takes models and avatars only, and an app's script is its blueprint's); references inside binary assets (a model's external image or buffer URI, which the loaders do not follow: models, avatars and emotes use their embedded data). Worlds that rely on any of these must run with `CLEAN=false`.
  - **What keeps a file.** Its name, found anywhere in apps, the blueprints that stay and collection blueprints (both as stored and as hydration loads them, with model and script cut at 2,048 characters), settings, user avatars, script storage (parsed, so JSON escapes are decoded; a copy set aside as unreadable is read as text), and the source of the code it follows, to a fixed point (a `.js` name the store listing leaves out, which holds content-hash names only, is asked of the store, at most 4,096 of them, and names nothing when there is no such file; one that is there but cannot be read stops the clean-up). The text is cut at every character a store name cannot hold, and a file is kept when a piece equals its name in any case, also percent-decoded (a run of up to 4,096 characters, at most 8 times), without dots, `_` or `-` at its ends, and with tabs, CR and LF inside it dropped (as the URL parser drops them), in one loop with the decoding (each pass drops them, then decodes once), so escapes and dropped controls in any order and position are undone, and what decoding brings in (`%09`, `%0D`, `%0A`) is dropped too. No URL is resolved for this, so a host, port, path prefix, `..`, query or CDN spelling cannot hide a name; ignoring case keeps what a case-insensitive file system loads from `asset://<NAME>`. A file named like a common word is kept whenever that word appears.
  - **When nothing is removed** (logged once; in these configurations cleaning never runs and the store only grows): a database row or `storage.json` does not parse as JSON, or a row has the wrong shape; `storage.json`, a set-aside copy or a script it must read cannot be read, including a store script that is missing, in every configuration (a CDN or cache in front of the store may still serve it), one that cannot be opened (the log names the blueprint), a file larger than the larger of `PUBLIC_MAX_UPLOAD_SIZE` and `STORAGE_MAX_BYTES` (read before, whole, up to Node's own limits), and an S3 script object stored with a content encoding other than gzip or deflate, with more than two codings or expanding past that size (the clean-up decodes gzip and deflate itself, also raw deflate and two stacked codings, which is more than the server's loader accepts; each stage is held to that size); a text holds a percent-encoded run longer than 4,096 characters or still encoded after 8 decodings (a store URL encoded once as a whole fits; deeper nesting used to be decoded at a cost that grew with the square of its length); `ASSETS_BASE_URL` is not clean: it must start with a lower-case `http://` or `https://` and have no query, fragment, userinfo, backslash, dot segment, empty path segment or trailing slash, in its normalised form (a relative, protocol-relative, `https:/host` or `?rev=` base stops it; start-up validation of the variable is unchanged); a database value (a row's data, the settings, an avatar) is larger than the read limit; more than 4,096 `.js` names are not in the store listing; a kept blueprint or collection blueprint has a script that is not a store file for certain. Only `asset://<name>` is one, or a URL that starts with a lower-case `http://` or `https://` (what both the runtime mapping and the server's loader take as remote), that the runtime leaves unchanged, with no userinfo and no `?`, `#`, `%`, backslash or `.`/`..` segment in its text, and whose normalised form is directly under `ASSETS_BASE_URL`. A script hosted elsewhere, a page path such as `/assets/x.js` or `blob/../assets/x.js` (a proxy may serve another application there), a spelling the runtime rewrites (`https:/host/x` becomes `https://https/host/x`, a tab in the scheme, `HTTPS://`, which the server's loader refuses) or a legacy encoded or query spelling all stop it. Only a value starting with a lower-case `blob:` (what `URL.createObjectURL` returns, and what the runtime leaves alone) is no script; `Blob:443/app.js` is fetched from a host named blob, so it stops the clean-up too.
  - **Assumptions.** The server process is the only writer of the store, the trash and the database while it starts (uploads are not accepted until cleaning has finished; other processes changing those files at the same moment are not supported). Database tables are read whole, as the world itself reads them when it starts; the read limit applies to each value, not to a table's total. The assets URL serves each store file's own bytes: a redirect, a rewrite or a cache in front of it that answers a file's URL with something else is not supported (the clean-up reads the store, the world loads what the URL serves). With the local store a removal is recoverable for CLEAN_TRASH_DAYS; with S3 it is not (turn on bucket versioning).
  - **The trash.** With `ASSETS=local`, removed files go to `<world>/assets-trash/<UTC date>/<name>` beside the assets directory (the same file system, so a rename; never served, never listed, on the disk the free-space check measures), one log line with the count and the folder. Folders at least `CLEAN_TRASH_DAYS` old by their UTC date (30 by default, so a file can go up to a day sooner than that after it was moved; `0` deletes at once and empties the trash, folders dated in the future included) are removed once discovery is complete, after anything trashed that is named again has come back from its newest copy that is still there (logged). If none of a named file's copies is there any more, that is logged and the trash is not purged that run. Nothing comes back while `ASSETS_BASE_URL` is not clean: the clean-up then stops before it looks. Before the purge, a kept file that is also trashed must still be in the store; if another process removed it, its trashed copy comes back, and if that fails the trash is not purged. With `ASSETS=s3` objects are deleted: turn on bucket versioning to keep a way back.
  - **Dry run.** `CLEAN=dryrun` changes nothing and names what would be removed (up to 50), what would come back from the trash, and which trash folders would be removed.
  - **No longer a stop.** A prop holding a non-string `url` (props accept any JSON) used to disable cleaning for the whole world; it is now just text.
  - **Cost.** Linear in the text: two walks over it without copying it, a percent-encoded run decoded at most 8 times and only up to 4,096 characters, every file read through one handle and counted up to the limit above, each place that holds an undecidable run recorded once (the log names the first 20). A world of 5,000 files and a 50 MB corpus is cleaned in under a second; 256 KB of nested encoding, or 40,000 places with such runs, stop it in a fraction of a second. The database tables are read whole (see Assumptions).

### Security
- server: any builder could start any number of AI actions at once, without end, each one or two requests on the operator's provider account (only the Anthropic client set an output limit); where every visitor is a builder (a world without an admin code), anyone could. Nothing counted them and the log did not say who asked. Actions now have a budget per builder and for the world and a deadline, every provider request has an output limit, and each started action is logged with what it is and who it is counted against. In a world open to all, user ids are free, so there only the world's limits hold: at the defaults, 60 actions an hour, at most 120 provider requests before the SDKs' own retries.
- server: `/status` (no authentication, readable from any origin) listed every connected player's user id, name and live position. It now gives a count. A client that joins the world still receives the players in its snapshot; what is gone is the list for anyone who merely asks over HTTP.
- server: Node.js 22.23.4 → 22.23.5 (Docker image, `.nvmrc`, engines): the security release of 2026-11-11. Of its sixteen fixes, none of the seven rated High is reachable in this server as it is built: they are in `http2` (not used: the server speaks HTTP/1.1 only), in TLS servers (it makes none: it listens in cleartext, and TLS ends in whatever is put in front of it) and in `https` servers (CVE-2026-123864 reads other connections' memory only over `node:https`; the advisory says cleartext `node:http` is not affected). The outbound `https.Agent` fix needs requests that differ in their `ca` option (ours never set one), the proxy-credentials fix a proxy configured from the environment, and the Permission Model fixes `--permission`. What applies without a named CVE is the bundled `llhttp` update: the parser of every request this server receives. Taken as routine hygiene, not as an emergency.
- server: a session token was the account for ever: no end, and no way to change the signing secret without resetting every identity. Tokens now end (see Changed) and the secret can be rotated with `JWT_SECRET_PREVIOUS`. Renewal does not cancel a token that leaked; only a new secret does. The signing algorithm is pinned to HS256 on verification (the library already refused unsigned tokens for a string secret; the pin also refuses the other HMAC sizes).
- server: wrong admin codes cost nothing. `/admin <code>` compared with `===`, and a wrong code was neither counted, delayed, answered nor logged, at up to about a thousand attempts a second per connection: a short code could be found by trying, unnoticed. Codes are now compared in constant time (SHA-256 digests, `timingSafeEqual`) and wrong ones are slowed down per user id, per address and per wider network, with one summary line in the log a minute after the first wrong code (never the code, never an address). This is a brake, not a wall: every new connection is a new user id, so only addresses hold a guesser, at about 1,400 guesses a day from one IPv4 address and 8,600 from one IPv6 /48. A six-digit code does not hold for long against that; 16 random characters do. Someone on an admin's own address can keep that address waiting; a stored admin rank needs no code.
- server: any visitor could make every other visitor's browser download and parse a file from any host. A player's session avatar and emote took any `http(s)` URL from any connection (`sessionAvatar` in a player's own update or the `avatar` parameter of the `/ws` URL; the emote in `e`), with the Custom Avatars setting on or off, and with it on, the stored avatar took one too and kept it for every later visit. Each client that saw the player fetched the file (up to 64 MiB for an avatar, 32 MiB for an emote): the sender learned every viewer's address and got their parser and their bandwidth. Now a URL outside the world (`isExternalUrl`: anything that, as the loaders read and resolve it, is not requested from the world's own store: an `asset://…` file, or an address under the store's own URL) is taken from a player only while the player is a builder, or when it is the very URL a server script chose for that player (the session avatar a script set, one of the last 16 emotes a script's effects carried). A refused emote becomes none; a refused session avatar is dropped and the sender's own view is set back. What this does not change: builders, and server scripts, can still name any URL; with Custom Avatars on a visitor can still upload a VRM of their own making, which everyone parses (size-capped, served from the world's store, with no references outside its own file). A server script that passes on a URL a visitor supplied gives that visitor the old reach.
- server: ten log lines printed an id or a setting's name from a packet with only its length cut, so a line break in it started a line of the sender's making in the server's log. They print it as `previewValue` does: quoted, printable characters only.

The server closed the world's connection and nothing more: the player reloaded and was back as the same user with the same rank, and since the voice room is a connection of its own that no client ever closed, everyone who already heard a kicked (or simply disconnected) player kept hearing them, at their last position, and kept seeing their screen share.

- server: the pages had no security headers at all. The world page asks for wallet signatures and sends tips, and any other site could show it in a frame under its own page and have a visitor click through it.
  - **Framing.** The pages (the world page, and the static pages on every answer, a 304 to a browser revalidating its copy included) say `Content-Security-Policy: frame-ancestors 'none'; base-uri 'none'; object-src 'none'; form-action 'self'` and `X-Frame-Options: DENY`: no other site can frame the page, and markup that got into it cannot change where relative URLs load from, embed a plugin or post a form to another site. Nothing on the pages uses what these forbid.
  - **A second copy of the world page.** `/index.html` was served as the built file, a working copy of the world page outside the route that serves `/`. Both names give the same page now.
  - **Uploaded scripts are text.** A `.js` file of the store was served from the page's own origin as `text/javascript`: its `sandbox` and download headers did not stop a `<script src>` or an import from running it with the page's rights, nor a worker in Chromium and WebKit (an engine that applies `sandbox` to a worker refused that one already). It is served as `text/plain` (the loaders read its text and evaluate it in a compartment, as before), which a browser with `nosniff` refuses for all three. With `ASSETS=s3` the type is stored with each object when the object is written: the built-in assets are written again at every start and get the new type, but a script uploaded before keeps `text/javascript` until its object's metadata is changed in the bucket or the object is replaced there (and a CDN in front may need invalidating). Uploading the same file again does not do it: the same bytes give the same name, and an object that exists is not written again.
  - **Every reply a route makes** says `X-Content-Type-Options: nosniff` (not a WebSocket upgrade, nor the errors the HTTP layer writes itself before any route runs: a 400 for a URL it cannot decode, a 408, a 431), and the pages say `Permissions-Policy: camera=(), geolocation=(), payment=(), usb=()`: in browsers that implement it (Firefox does not), the page and what it frames cannot use the camera, the location, the Payment Request API or a USB device. `payment` is that API only: wallet requests do not go through it. `Strict-Transport-Security` is sent only when `HSTS_MAX_AGE` (seconds) is set.
  - **What this is not.** It is not a policy on scripts, styles or connections: markup that got into the page could still run a script, and the page may connect to and load images from any host (app scripts and avatars name their own). A full policy needs `eval` for app scripts and has to be tried against real wallets before it is enforced; it is planned as a report-only header first. The script editor still loads Monaco from cdnjs when a builder opens it: whoever controls that CDN runs code in that builder's page. CORS stays open on the API (session tokens are not cookies, so another origin cannot act as a user).
- scripts: `world.chat()` can no longer post as a player or as the world (CDX-09). Every chat message has a host-assigned `kind`: `player` (stamped by the server on each `chatAdded` packet, whatever it claims), `app` (a script: no `fromId`, the app's blueprint name in `app`), `system` (command replies and notices) or `tip` (the server's confirmed-tip announcement and the private recipient notice). A `data:` buffer is decoded by the same decoder, charged at its size, its data at least the buffer's byteLength (checked before parsing, with that decoder: a shorter one threw inside the parser), and not fetched either: its old charge, three quarters of the URI, was below what a fetch made of a payload that is not base64 (1,000 bytes from 1,006 characters, 3,000 from 1,000 characters past ASCII). Without a budget (the server) both are fetched as upstream. The `data:` scheme is recognised in any case, as RFC 3986 says, by one test that the check, the parser, the budget and the client's URL filter share (an upper-case `DATA:` was a relative URI to the check, data to the parser and the budget, and refused by the filter). A value they treat as a string must be one (a material's name given as a list was joined into a string for every outline three-vrm cloned from it), a sampler's filters and wrapping and an accessor's component type are numbers, and an image's `mimeType` is one of a fixed list, image/png, image/jpeg, image/webp, image/ktx2 or image/avif (the last two the types of the images KHR_texture_basisu and EXT_texture_avif name; an optional KTX2 or AVIF image is skipped for its fallback): each texture's userData keeps it, and three-vrm copied a 100,000-character one into nine slots of every outline (180 MB from a 0.11 MB file, 0.88 MB counted). Extras are small by rule: an object's extras and extensions (node, mesh, primitive, material, image, scene, camera, light; the parser copies them into its userData), at most 64 KiB of JSON (the most in those files: 1,957), and all the userData the parsed scene holds (a mesh's for each of its primitives and each node using it), which every clone of the scene copies, an avatar's for each player, at most 8 MiB (the most in those files: 22,501; an instanced Blender export with custom properties, one mesh of 5 materials with a 200-character property on 1000 nodes, holds 1,055,000, and was refused at the 1 MiB first set). Strings inside extras, and inside extensions nothing here reads, are not names: they are within those sizes. A URI has no line break (`\n`, `\r`, U+2028, U+2029), and a `data:` URI has the shape `data:[<type>/<subtype>][;<name>=<value>]...[;base64],<payload>`, the part before the comma a name (at most 1024 characters): base64 broken into lines, a space before `base64` (`data:image/png; base64,…`, which some fetches accept) and base64 with %-escapes (which browsers decode first) are refused, and so is a payload that is not base64 with a raw control character, a space, a character past ASCII or a `#` (the forms on which a URL parser and a decoder disagree). A texture has an image this client decodes, its source or a WebP one: an optional KTX2 or AVIF texture without a fallback source failed in the parser with a TypeError. A root shared by several scenes is valid glTF and loads: it ends in the last, each move charged. Draco and meshopt compression are accepted when optional (the parser reads the fallback data; an optional Draco extension without a decoder used to fail the load). Accessors must be what the parser and three.js assume of them: an animation sampler's times one float a keyframe and its values one per keyframe (three for CUBICSPLINE, one per morph target for weights) of the path's type, neither interleaved, so a track's value size is a whole number (7 values for 2 CUBICSPLINE keyframes, a value size of 3.5, made three's interpolant loop forever, and so did times at a byteStride of 8, which reached the track as twice the floats); a skin's inverse bind matrices a float 4x4 matrix per joint, not interleaved; a primitive's attributes, and its morph targets, of one count, its indices unsigned and not interleaved, and every primitive of a mesh with as many targets; instancing attributes of one count, at most 16 on a node (the parser goes through each for every primitive); every bufferView within its buffer (its byteLength, and the bytes the buffer really holds: a `data:` buffer's decoded data, the GLB's binary chunk; past them the parser threw "Invalid typed array length"), every accessor at least one element, within its bufferView, strides and offsets by the specification's rules, and sparse entries no more than its elements. three-vrm, which is not vendored, is bounded by its work counted in the units its plugins iterate. Most of them walk the parsed scene graph, so the units are its objects, not the document's nodes: a mesh of several primitives is a Group and a mesh per primitive, spring colliders are added below their nodes, expressions and the humanoid rig to the scene (a bone listed once on a node whose mesh has 21 primitives made 23 joints, counted as one). Counted: expressions, bind objects, the primitives they refer to, the steps they take (each morph bind walks its node's subtree, each VRM 0 material value the scene), spring joints and colliders, joints x the colliders of their groups, sorting the joints, first person (every node, the subtree of each with a mesh, the annotations), node constraints, the draws MToon outlines add (two per outlined mesh on a geometry the parser shares between meshes with the same primitive: 300 such meshes drew 180,000 groups), and what the outline material three-vrm clones for each outlined primitive copies, up to 16 MiB: the material's userData (its extras and the extensions the parser does not handle), and for each of MToon's 10 texture slots the largest texture userData in the file, an image's extras and its mimeType (which image a slot holds is not modelled: an extension's source, the parser's texture cache and VRM 0's slots can each resolve it to another), each copy at that estimate (50 outlined primitives on one material with 1000 small objects in its extras made 50 copies of them, about 1 MB, while nothing was charged); and what an expression's texture-transform binds copy, up to 16 MiB: each clones every texture slot of each material it binds (up to 8, a MeshStandardMaterial's), once per mesh the material is on (VRM 1) or per material named and its outline copy (VRM 0). These counts are computed from the document before three-vrm runs, and three-vrm is not metered as it runs: springColliders, constraints and the VRM 1 spring joints and morph binds are exact; the others are bounds, each at least what it stands for (`gltfLimits.js` says why for each).
  - **Transfers at once.** At most 8 downloads from the world's store and 4 from other hosts run at once (each pool on its own, so slow hosts cannot hold up the world's assets); the others wait without a connection, and their deadlines start when they do. That is the bound on bytes in flight: each transfer stays within its kind's limit (a stated length over it is refused before reading, a body that grows past it is cut off), so downloads from other hosts hold at most 4 x 64 MiB = 256 MiB at the very worst, and the world's own at most 8 times the upload limit (or the kind's limit, if larger). At most 256 loads from other hosts may wait or run; past that a new one fails at once and is not kept. The world's own loads are not capped in number.
  - **Late downloads.** A transfer is filed from the moment it is asked for: a file picked or set for its URL while it waits for a slot or downloads is the one kept (and, once the slot is granted, the one used), and a download that finishes after `destroy()` writes nothing. `destroy()` aborts the downloads in progress and fails the waiting ones; a request asked for just before it fails without taking a slot in the next lifecycle.
  - **Avatar skeleton.** The bone taken out of the scene as the skeleton's root is the one above the hips, not the first joint the file lists. With the joints listed head first, the head was taken out and the hips were moved twice (a probe placed at X = 10 reported the hips at X = 20). An avatar whose head is not below that root is refused; stray bones outside it are accepted.
  - **Images without a size.** An image or texture whose intrinsic width or height is zero fails its load.
  - **Image sizes from headers.** The size of a PNG, JPEG or WebP is read from its header before anything decodes it, so a header of a few dozen bytes declaring 100000 x 100000 no longer reaches the decoder. The reader walks the PNG chunks to the image data, the JPEG markers to the first scan and the WebP chunks; a file that is inconsistent (a second IHDR, an APNG frame outside the image, a second JPEG frame header in front of the real one, which decoders read differently, a WebP image or frame that does not match its canvas) is refused everywhere as malformed. Stand-alone images and textures (the world's store and other hosts, loaded or just picked) are refused there when over 36 megapixels, without a size or malformed. Other formats (GIF, AVIF, SVG, BMP) go to the browser's decoder as before and are checked once decoded. Inside a model, avatar or emote the parser sizes each image at the place it is about to decode it, so what is charged is what is decoded: images the parser shares (textures on one bufferView with one sampler) are one decode, and an image only a KTX2 texture would use is not decoded at all. A file's decodes together may have at most 256 Mi pixels (sixteen 4096 x 4096 textures, about 1 GiB decoded); the bundled avatar decodes 4 Mi. An embedded image named by a `blob:` URL is refused. The decoded size is still checked afterwards, on both paths.
  - **Memory.** Files and results for URLs outside the world's store are kept up to a bound, least recently used first out; a load still in progress is not dropped, and a dropped or replaced one no longer writes its result back. Video loads are kept under the same bound. A decoded image releases its object URL, which used to keep the downloaded bytes alive for the life of the page. Bytes that do not decode are not kept, so the next load downloads them again.
  - **Files just picked.** A file inserted before its upload (the file fields, a dropped model or avatar, `.hyp` import) is checked and decoded as a download is: a broken image fails instead of staying pending, and a failure is not kept.
- server: a builder could make the world impossible to join, and keep it that way across restarts. App entity ids had no length limit and nothing bounded how much the apps add to the join snapshot, so 36 `entityAdded` packets with 30,000-character ids (or about 7,300 ordinary ones) pushed the snapshot over its 1 MiB cap; every later join then failed, admins included, until the database was edited by hand.
  - **Ids.** A new app's id is 1 to 64 characters of `A-Z a-z 0-9 _ -` (what the client generates fits) and cannot be the id of any user this world knows, present or away (players and apps share one id space, and an app holding an absent user's id would have collided with that user's next join). The server keeps the user ids in memory for that (about 60 bytes each: 6 MB for 100,000 users). It refuses a second entity with an id that already exists, and a `blueprintAdded` for an id that already exists (changing a blueprint takes `blueprintModified` and its version rule).
  - **An app that already holds a user's id** (stored before this rule) moves to a new id when that user joins: it is removed and added again under the new id with its blueprint, transform, pinned flag and state (state a script made unreadable becomes `{}`), broadcast, and logged once with both ids. The player joins as usual. The move cannot lose the app: the new row and the old row's removal are written in one transaction, so a stop leaves the app under one id; a failing app teardown does not stop it. (The server's database is always knex on SQLite or Postgres, which has transactions. Only a stand-in database without them, in tests, writes the new row first and can be left with the app under both ids, which nothing merges at start-up.)
  - **World budget.** Blueprints, app entities, settings and collections together may take 768 KiB of the join snapshot. A change that would go past that is refused the way an over-budget blueprint already was (the sender's copy is reverted, one log line per connection), whether it comes from a client, a server script or the AI, and a settings change too. A blueprint change that rebuilds its apps counts the client-set app state it empties. The 512 KiB blueprint budget still applies.
  - **The rest fits by construction.** What no budget tracks is dropped from a snapshot that does not fit, one step at a time and only as far as needed: the voice state of players who left, the chat history, players' effects, app state a server script assigned, and last other players' avatars and emotes (the joiner sees the default avatar until their next change). What cannot be dropped is counted as at most 1 KiB per player (measured worst case 695 bytes) plus the snapshot's fixed part: the joiner's own record, the URLs, the upload size, the AI names and the session and voice tokens. The fixed part is measured, not assumed: the server measures it at start-up for the largest joiner its configuration can have (8,811 bytes for `.env.example`, 9,378 with LiveKit, 18,903 with a 4,096-character `LIVEKIT_API_KEY`) and logs when it is over the 24 KiB expected, and each join measures its own. The snapshot carries the upload size as the number the server parsed (a `PUBLIC_MAX_UPLOAD_SIZE` padded with zeros used to be sent as written). The steps taken are logged once per combination.
  - **Joining.** A join is admitted when the real snapshot, after its steps, fits the cap; that is the only hard condition, and a snapshot that cannot fit is refused with the `player_limit` kick before any player is added (it used to close with 1011). The counted world state is an upper bound: a world stored over its budget (for example 5,100 apps: 1,035,412 bytes counted, a 592,143-byte snapshot) still takes a user with a stored rank, so an admin can come in to shrink or moderate it.
  - **Visitors.** A joiner without a stored rank of builder or above (the rank on the user's row; a free-build world rank, admin for everyone without `ADMIN_CODE`, and a session-only token grant do not count) must also leave room: with them here, the bound W + fixed part + P × 1 KiB ≤ 1,047,552 must still hold for 8 more players and 64 KiB more world state. Otherwise they get the `player_limit` kick (logged once per reason), before `WS_MAX_SOCKETS` or `playerLimit` would refuse them. A full 768 KiB world takes 174 visitors and an empty one 940 (159 and 925 with a 24 KiB fixed part); after them, 73 ranked users fit the bound at the full world, and 64 KiB of growth and 8 ranked users at the empty one. So 231 visitors can no longer keep an admin out, and 998 can no longer stop a 1 KiB addition. `connectionLimits` has no rank reservation of its own: `WS_MAX_SOCKETS` still counts every socket.
  - **Growth.** World growth is admitted against the players present (at least 64) with the measured fixed part, so 64 players always fit a world at its budget. To keep the counted parts bounded, the server refuses to start with `ASSETS_BASE_URL`, `PUBLIC_API_URL` or `LIVEKIT_WS_URL` longer than 1,024 characters or `AI_PROVIDER`, `AI_MODEL` or `AI_EFFORT` longer than 128, and a joiner's own stored avatar longer than 2,048 characters (only legacy data can be) falls back to the default.
  - **Existing worlds.** A world that is already over the budget loads whole, reports its totals and five largest items at start-up, and may shrink but not grow. When the counted total is over the snapshot cap too, the report says so as a count: visitors are refused, and a user with a stored rank joins while the real snapshot fits. Nothing stored is dropped or rewritten.
- server: a blueprint's `script` or `model` could name any file the server can read. Builder rank (which holding the token can give) was enough to set `script` to `/proc/self/environ` or `asset://../../x`. The server then read the file on every rebuild, and the AI `edit` and `fix` actions sent its text to the AI provider and saved the reply as an asset, so the server's secrets could leave through the AI. `model: '/dev/zero'` could exhaust the server's memory, and node agents read such paths on their own machine.
  - **Loading.** The server and the node agent read a local file only for `asset://<name>` (letters, digits, `.`, `_` and `-`, up to 128 characters), and only from directly inside the assets directory. No other value is ever read from disk. A path (`/…`), `blob:` and an invalid `asset://` name are refused with the reason and a short prefix of the value. With `ASSETS=s3`, and on the node agent, `asset://<name>` still loads from the assets URL. Remote loads are unchanged: an http(s) URL is fetched, and so is what the loader has always turned into one (`//host/x` and a bare `host/x` become `https://…`, which includes spellings such as `file:///x`); limiting where the server may fetch from is a separate change.
  - **Blueprints.** A new blueprint, or a change that sets `model`, `script` or `image.url`, must give `asset://<name>` or an http(s) URL with a lower-case `http://`/`https://` prefix. The client refuses anything else with a toast, the server with a revert. A stored blueprint that already holds another value still loads as it is, and changes to its other fields are accepted.
  - **AI.** `edit` and `fix` read only an `asset://<name>` script. For any other value nothing is read or sent to the provider, and the refusal is logged as the action's failure.
  - **Start-up.** Each stored blueprint whose `model` or `script` the server now refuses is logged once (`[network] blueprint "<id>" keeps a source the server no longer loads; …`) and kept unchanged. On the server that app shows the crash block until a builder replaces the value.
- scripts: the classes app scripts can reach are frozen. Before this, a script could replace a method on a shared class (`Vector3.prototype.add = …`), and the engine and every other app then ran the replacement, on the server and in every visitor's browser, until the process restarted.
  - **What is frozen.** `Vector3`, `Quaternion`, `Euler`, `Matrix4`, the interpolation classes and `Curve`, and the classes their instances lead to (THREE's own `Vector3`, `Matrix3`, `Keyframe`, and `Color`, which a material proxy returns): constructors, statics, prototypes and the methods themselves. Any write throws a `TypeError` in the script.
  - **Pointer callbacks.** `onPointerEnter/Leave/Down/Up` receive a new frozen `{ type, stopPropagation }` object for each call. The engine used to pass one shared, mutable event object to every app.
  - **XR poses.** Controller poses are copied into the pose objects as numbers. The browser's `DOMPointReadOnly` used to be passed to `copy()` of an object a script holds, whose `copy` the script can replace.
  - **`Object3D` is no longer given to scripts.** THREE's `Object3D` hands every listener the same event objects, through which a script could receive each object the engine later adds to its scene (and from a texture, the page's `document`). It was not documented; scripts use nodes for hierarchies.
  - **How.** Each prototype property is first turned into an accessor that still lets an instance take its own value (`src/core/extras/scriptClassPrep.js`), because THREE and the engine assign over prototype properties on instances (`_onChange`) and in constructors (`isVector3`). A plain freeze makes `new Object3D()` throw.
  - **Tests.** `test/scriptClassHardening.test.js` runs 24 attacks in real compartments under the real lockdown, checks that the engine and every node type still work, and walks everything reachable from a script's globals, instances and node proxies. The old test passed over an empty class list.
  - **Not covered.** A script can still obtain one of the math classes' internal temporary objects (for example through `Matrix4.decompose` with a made-up quaternion) and change that one object. That can disturb math for others; it gives the script nothing it could not already do to availability.
- server: the unused `Comput3Client` in `src/core/systems/ServerAI.js` is removed, together with the Comput3 API key written into it.
  - **Origin.** The class and key came from upstream Hyperfy (commit `57ee205`, 2025-08-20). The key was not issued for this project, so rotating it is up to whoever holds that Comput3 account.
  - **Not used.** The class was never constructed; the AI providers are still chosen by `AI_PROVIDER`, with `AI_API_KEY`.
  - **Still visible.** The key remains in this repository's history and in upstream.

### Still open
- nodes: `SkinnedMesh.unmount` does not clear `this.action`, so after a remount `play()` of the clip that was playing returns early and nothing animates.
- nodes: the SkinnedMesh `castShadow`/`receiveShadow` setters rebuild only when `this.handle` is set, which a SkinnedMesh never sets: a change after mounting is not applied.
- nodes: a video's unmount disposes its mesh geometry, which other nodes may share.
- nodes: a `uitext` under a `ui` throws on the server (`insertChild` of undefined: the server's `ui` has no layout node).
- nodes: in the Node test harness a box mesh made with `app.create('mesh', { type: 'box' })` inserted nothing (`Mesh.mount` returns early without `_geometry`); not yet checked in a browser.
- Phase 2: method shadowing with host (non-native) arguments remains for the objects a script makes and passes in (the THREE prototypes themselves are frozen, and the engine's own math objects a handle gives out are sealed, see Security), including interpolation, query/player getters and transitive matrix decomposition. Shared query vectors and live temporary output vectors remain script-reachable. The sentinel must be revisited when prototypes are hardened.
- Healthy physics shapes still do not resize on later scale edits (a skipped one mounts again once its transform changes).
- Persisted app repair and finite float32 checks at converted PhysX pose boundaries do not validate arbitrary script-composed transforms or every geometry. The player-transform hotfix already closed the octree expansion hang.
- Pending asynchronous native continuations after fatal shutdown remain a Phase 3b-1 residual; stopping ticks is not a global cancellation of native work. Generation-bound physics capabilities and a full teardown transaction are deferred. Emscripten abort state requires a restart; the dormant `prim-physics-test` example's direct PHYSX usage remains a follow-up. XR physical movement requires code review/headset verification.
- Model, avatar and emote limits: cost inside three.js and three-vrm that multiplies in ways the parser's charges do not capture is not proven absent; each review so far found another such place. Strings and extras are now small at the door, so what is copied, scanned or keyed once per object is at most 1024 characters a string and 64 KiB an object; what that still multiplies is bounded, not charged: three-vrm compares each VRM 0 material value's name, with " (Outline)" appended, against every material in the scene (at most 1024 characters a comparison, the walk counted); and each clone of a parsed scene after the parse (an avatar for each player) copies its userData, up to 8 MiB of JSON: about 180 MB held for the worst shape (lists of empty objects, 64 KiB an object), for each clone; an instanced export with small custom properties holds a few MB. The time limit refuses at the next charge after 10 s, but one long loop inside a library runs to its end, on the main thread. Up to 2^26 steps of work plus one per byte, and up to 10 s, may run on the main thread before a refusal (a file built to reach the work limit through one walk is refused after about 1.4 s on a desktop; a phone is slower). The server applies the same check and budget to models and emotes (it builds no avatars), with the morph-target charge at its largest since it has no renderer; its 10 s limit, like a client's, cannot interrupt a loop inside a library. The limits are per file and sized for VRoid avatars, 320 MiB of allocations beyond twice the file: with up to 12 files parsing at once inside the transfer slots (and files a user just picked taking none), a world of hostile files can hold several gigabytes at once before each is refused. Most of a VRoid avatar's cost is the morph textures three.js builds for each face geometry over all of the face's vertices; three-vrm's `VRMUtils.removeUnnecessaryVertices` would cut that, and the client does not call it. An avatar with far more blend shapes than VRoid's 56 (a "perfect sync" face of over 100, on as many primitives) may need more than the byte limit; none was measured. VRoid can export 4096 x 4096 textures, which have about twice their size to spare under the 36-megapixel limit per image (the samples' largest is 2048 x 2048). The time counts waiting too (an image decode, other parses interleaved), so a slow device loading many files at once could refuse a large honest one. Values inside the binary data are not read before parsing: index values beyond the vertex count, joint indices beyond the skin (a TypeError when the avatar is measured, so it fails to build), NaN or huge floats. three-vrm is bounded by counts computed before it runs; it is not metered while it runs. After parsing, turning a model into world nodes, cooking physics meshes and uploading to the GPU are bounded only by what was charged (sizes), not in time.
- Visitor-supplied avatar/emote assets can still contain invalid/extreme numeric data and corrupt that player's avatar, bones, nametag or bubble. Octree parking prevents those bounds from hanging the tree; it does not repair the asset. Asset numeric validation and an avatar fallback/cache lifecycle remain follow-ups. Voice positioning uses the validated player base transform rather than avatar bones.
- Shared positions beyond `1e6` per component are not broadcast; local movement is not constrained or corrected by this hotfix.
