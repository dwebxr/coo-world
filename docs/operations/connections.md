# Connections and inbound packets

- Per client address, `/ws` admits `WS_CONNECT_BURST` new connections at once (default 20) and `WS_CONNECT_RATE_PER_MIN` sustained (10/min), with at most `WS_CONNECT_CONCURRENT_PER_IP` open at a time (8). IPv6 also has `WS_CONNECT_CONCURRENT_PER_56` (16) and `WS_CONNECT_CONCURRENT_PER_48` (32) concurrent limits. Its parent rate buckets use `WS_CONNECT_RATE_PER_MIN_56=20`, `WS_CONNECT_BURST_56=40`, `WS_CONNECT_RATE_PER_MIN_48=40` and `WS_CONNECT_BURST_48=80`. Setting either rate or burst to `0` disables that parent bucket. Every bucket and concurrency cap must pass before any tokens are charged. `WS_MAX_SOCKETS` (64) caps all admitted transports, including closing sockets, until TCP closes. `0` disables a limit; `WS_CONNECT_BURST=0` also requires `WS_CONNECT_RATE_PER_MIN=0`. Raising `WS_MAX_SOCKETS` raises the total write-backlog bound of 68 MiB at the default (64 MiB for its 64 connections and 4 for the places kept for ranked users, below); setting it to `0` removes that bound. `WS_CONNECT_MAX_TRACKED` (40000) bounds the shared table of address and IPv6 parent buckets; newcomers are refused while the table has no idle entries. Refused upgrades receive HTTP 503 with `Retry-After: 10`, before any database lookup or snapshot. Ordinary HTTP GETs take no slot. Addresses are read as for [uploads](uploads.md) (`UPLOAD_CLIENT_IP_HEADER`, `Fly-Client-IP` where `FLY_APP_NAME` is set, or the socket address); IPv6 uses `/64`, and both IPv4-mapped spellings count as IPv4.
- Places kept for ranked users: `WS_RESERVED_SOCKETS` connections beyond `WS_MAX_SOCKETS` (default 4, a whole number from 0 to 8; `0` turns them off), and as many players beyond the world's `playerLimit`, are kept for users whose rank stored with their user is admin (`WS_RESERVED_RANK=admin`, the default; `builder` lets builders share them with admins). Only the stored rank counts, never a world's rank setting or a token's builder grant, and where admin is open to all (no `ADMIN_CODE`, with `ADMIN_OPEN=true` or outside production) there are no kept places at all; the server says which at start-up. When an address's own limits or `WS_MAX_SOCKETS` refuse an upgrade, the server reads the session token in its query (`authToken`): one longer than 512 characters, or naming a user without that stored rank (the server keeps the stored ranks in memory: read at start-up, changed with every rank given or taken), is refused at once; otherwise its signature is checked, and a verified ranked user is admitted while fewer than `WS_MAX_SOCKETS` + `WS_RESERVED_SOCKETS` connections are open, with at most 2 of theirs on this path and the address rate under their user id. Visitors are still held to `WS_MAX_SOCKETS` connections in all, the kept places' included, so the kept places take nothing from them. The join then reads the user's row: a connection let in on a kept place whose user's row does not have that rank, or is gone, is refused with `player_limit` before any user is made. A user let in on a kept place, and one refused there, is logged once per user id; the token never is. Behind a proxy with a connection limit of its own (Fly's `hard_limit`), that limit has to leave room for `WS_MAX_SOCKETS` + `WS_RESERVED_SOCKETS` and the other requests, or the proxy refuses first. What they do not do:
  - Kept places are a count inside the server, applied after an upgrade request has been read: they do not help when the process cannot accept or read requests at all (CPU saturated, file descriptors exhausted, the platform proxy's own connection limit reached).
  - A user with a stored rank of admin is let in through a kept place only on a session token the server verifies at the door; whoever holds a copy of that token is that admin, can use those places (2 per user) and can keep the real user out, until another admin lowers that user's rank or the operator changes `JWT_SECRET`.
  - Admins are no longer held to their address's connection limits, but to 2 connections and the address rate under their own user id; behind an address under attack they still need the server to accept their request.
  - Getting in does not end a flood: a kick holds back that user id (and, with `KICK_BY_ADDRESS`, new users from that address), and the attacker's next connection takes a visitor's place again.
  - A rank given or taken while the server runs counts at once; a rank edited in the database while the server runs is not seen at the door until a restart.
  - Once `WS_MAX_SOCKETS` + `WS_RESERVED_SOCKETS` connections are open, admins are refused like anyone else, and where admin is open to all there are no kept places.
  - At the door, a token naming a ranked user costs the server one signature check (two with `JWT_SECRET_PREVIOUS`), about the same CPU as reading the request itself; any other token costs a decode.
- A client message above 64 KiB closes the connection (1009). Below that, every packet is checked before its values are built: `entityEvent` (a script's `app.send`) up to 64 KiB; `blueprintAdded`, `blueprintModified` and `ai` up to 64 KiB and only from builders; everything else up to 32 KiB. Each connection has a token bucket of 2048 units refilled at 1024 a second; a packet costs one unit plus one per full 2 KiB and one per 32 decoded nodes, including failed scans. A refused packet is counted and logged once per connection and reason; the connection stays open. A blueprint, including its props, must fit in 64 KiB; an oversized change is refused in the client with a toast. On a world whose settings grant builder rank to everyone, every connection counts as a builder.
- All world blueprints together have a 512 KiB budget (`WORLD_BLUEPRINT_BYTES`), measured as the sum of their encoded server `blueprintAdded` packets. An add that exceeds it is refused and its optimistic entity removed; a modification that exceeds it is reverted. Existing worlds over budget still load with a warning and permit changes that do not grow the total. Blueprints, app entities, settings and collections together have a 768 KiB budget (`WORLD_JOIN_BYTES`, `src/core/extras/joinBudget.js`, with the same growth-only rule), so the join snapshot always fits its 1 MiB cap: what no budget tracks (chat history, players' effects and avatars, app state set by server scripts, voice state of players who left) is dropped from a snapshot that would not fit, step by step, and logged; what cannot be dropped is counted as 1 KiB per player plus the snapshot's fixed part, which the server measures at start-up for its configuration (about 9 KiB; it logs when that is over 24 KiB, which a very long `LIVEKIT_API_KEY` can cause). World growth leaves room for the players present (at least 64). A visitor (no rank of builder or above stored on the user) is refused with `player_limit` once their join would leave less room than 8 more players and 64 KiB of world growth need, so a crowd of visitors does not use up the room the join budget keeps for ranked users and for building: a full world takes about 174 visitors, an empty one about 940, whatever `WS_MAX_SOCKETS` allows. A user with a stored rank is admitted whenever the real snapshot fits, also in a world stored over its budget, so the join budget does not keep an admin out of a world that needs shrinking or moderating. The connection limits above are another matter: beyond the places kept for admins (`WS_RESERVED_SOCKETS`, above), they refuse an admin like anyone else. Builders should keep large text out of props.
- The strict plain-msgpack decoder counts nodes at admission and builds values when the inbox is flushed. Fair per-socket scheduling spends at most 9,216 work units per tick (`work = nodes + floor(bytes / 128)`); under a full flood, a socket waits up to about 2 s for service at the default 64 slots. Each inbox has a guaranteed 160 KiB reserve and can grow to 1 MiB using a 16 MiB shared pool. Server-to-client output is capped at 512 KiB per packet and 1 MiB of backlog per client. The initial snapshot alone may use up to 1 MiB minus 1 KiB of write overhead (`SNAPSHOT_CAP`); crossing half that size logs a warning once per process. Scripts share 512 KiB of output per tick and skip recipients whose backlog would exceed 512 KiB. The protocol is now `v=2`; old tabs must reload. See [app.send](../scripting/app/App.md#sendname-data-skipnetworkid) for data types and return values.
